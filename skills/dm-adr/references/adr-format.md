# ADR 格式规范

## 文件位置

每个 ADR 独立存放于 **`docs/adrs/adr-NNN.md`**，`docs/adrs/README.md` 为导航索引。

> 多文件 vs 单文件：多文件便于独立引用、按需加载和 Git 历史追溯。对于需要频繁增删的中大型项目，多文件 ADR 比单文件更易维护。

## 字段定义

### ADR-NNN

格式: `ADR-` + 三位数字（如 ADR-001, ADR-012）

- 从 001 开始递增，不跳号。
- 数字不计入域名或模块区分。

### 标题

简短名词短语，如：
- "Web 端域名选择"
- "云基础设施选型"
- "TTS 语音合成服务选型"

不使用动词开头（不是"选择 TTS 服务"，而是"TTS 语音合成服务选型"）。

### 状态

| 状态 | 含义 | 使用场景 |
|------|------|----------|
| `提议中 (Proposed)` | 已提出，正在讨论 | 新决策草案 |
| `已接受 (Accepted)` | 已批准，正在执行 | 已达成共识 |
| `已废弃 (Deprecated)` | 不再适用 | 技术栈迁移、策略变更 |
| `已替代 (Superseded by ADR-NNN)` | 被新的 ADR 取代 | 更优方案出现 |

状态更改时：
- 不删除旧状态，用 `~~删除线~~` 标记
- 示例: `- **状态**: ~~已接受~~ 已替代 (Superseded by ADR-007)`

### 日期

ISO 8601 格式: `YYYY-MM-DD`

记录决策做出的日期，而非记录写入的日期。

### 背景 (Context)

必须回答:
1. 当前面临什么问题？
2. 有什么约束条件？（技术、成本、时间、团队能力）
3. 有哪些可选方案？

2-5 句话即可。

### 决策 (Decision)

一句话 + 关键细节:
- "采用 XXX 作为 YYY"
- 核心配置参数（如有）

### 原因 (Reason) — 可选

解释选择逻辑：
- 为什么是 A 而非 B？
- 考量了哪些因素（性能、成本、团队熟悉度、生态、可扩展性）？

如果背景部分已解释清楚，可省略。

### 后果 (Consequences)

使用 emoji 前缀分类：

| 前缀 | 含义 |
|------|------|
| ✅ | 正面影响 / 好处 |
| ⚠️ | 注意事项 / 负面代价 / 风险 |
| 🔧 | 需要跟进的具体行动项 |

每条一个要点。

### 替代方案 (Alternatives) — 可选

如果讨论过多个方案，用表格对比：

```markdown
| 方案 | 优点 | 缺点 |
|------|------|------|
| 方案名称 | ... | ... |
```

### 相关 (References)

- 链接到相关文档（项目内用相对路径）
- 链接到相关 ADR（如 `./adr-002.md`）
- 链接到外部资源（官方文档、博文）

## 书写原则

1. **简洁 > 详尽** — ADR 是决策日志，不是设计文档。懂的人扫一眼就能懂，新人花 2 分钟能看懂背景和后果。
2. **事实 > 观点** — "MiniMax 中文语音 MOS 评分 4.5" 而非 "MiniMax 语音很好听"。
3. **不可变** — Accepted 后的 ADR 不能修改（除了状态变更）。如果想改主意，创建新的 ADR 取代旧的。
4. **独立可读** — 每个 ADR 可以脱离对话上下文独立理解。

## 完整模板

```markdown
# ADR-NNN: 决策标题

- **状态**: 提议中 (Proposed)
- **日期**: YYYY-MM-DD

## 背景

描述当前面临的问题、约束条件和可选方案。

## 决策

采用 XXX 作为 YYY。

## 原因

解释选择逻辑。

## 后果

- ✅ 正面影响
- ⚠️ 注意事项 / 风险
- 🔧 需跟进事项

## 替代方案

| 方案 | 优点 | 缺点 |
|------|------|------|
| ... | ... | ... |

## 相关

- [文档链接](./path/to/doc.md)
```

## README.md 维护

每当新增或更新 ADR 时，需同步更新 `docs/adrs/README.md`：

1. 在表格中新增一行
2. 如需，在"按领域浏览"下添加/调整分类
3. 更新旧 ADR 的状态（如被替代）

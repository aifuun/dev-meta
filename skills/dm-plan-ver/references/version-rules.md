# Version Rules — 版本目录文件规范

本规范定义了每个版本目录下的标准文件结构、职责分工和基于 Transaction Flow 的写作方式。

---

## 1. 目录结构

```
docs/versions/vX.Y-<slug>/
├── 200-spec.md        # 考什么：交付目标与验收标准
├── 300-design.md      # 为什么这么设计：流程串联、模块分工、架构决策
├── 400-build.md       # 怎么造：实现蓝图 + 执行顺序矩阵
└── 500-schedule.md    # 排程：工作包列表与执行顺序
```

### 创建顺序

> 版本级四文档按以下顺序创建，每步都是下一步的前置条件：

| 顺序 | 文档 | 回答的问题 | 前置依赖 |
|------|------|-----------|----------|
| 1 | `200-spec.md` | 交付什么？怎样算完成？ | — |
| 2 | `300-design.md` | 流程如何串联？模块如何分工？ | spec |
| 3 | `400-build.md` | 怎么实现？怎么执行？ | design |
| 4 | `500-schedule.md` | 什么时候做什么？按什么顺序？ | build |

---

## 2. 各文件职责

| 文件 | 受众 | 回答的问题 | 关键内容 |
|------|------|-----------|---------|
| `200-spec.md` | PM / QA / Dev | 这条 Transaction Flow 要交付什么？怎样算完成？ | 目标、交付范围、**架构锚点（分层/模块/门面/契约/API）**、功能验收标准、架构验收标准、DoD |
| `300-design.md` | 架构师 / Dev | 各 Transaction Flow 如何衔接？各流负责什么？ | 流程切分、顺序、模块关系图、关键架构决策与原因 |
| `400-build.md` | Dev | 每个 Flow 怎么实现？按什么顺序执行？ | 流内步骤、函数签名、Schema、异常策略 + 执行顺序矩阵（依赖、并行/串行） |
| `500-schedule.md` | PM / Dev | 工作包如何排期？按什么顺序执行？ | 工作包列表（跨领域）、类别、环节、难度、预估工时、验收标准、状态。dev 工作包以 TF 为原子单位，完成定义含代码+部署+联调 |

### 2.1 四件套分工总览

```
200-spec    → 考什么（验收标准）
300-design  → 为什么这么设计（架构决策）
400-build   → 怎么造（实现蓝图 + 执行顺序矩阵）
500-schedule → 排程（什么时候做什么）
```

**200-spec.md** — 为什么做、做什么
- 业务流总览：版本目标、TF 覆盖范围、明确不做的事
- TF 清单：每个流的编号、名称、一句话目标、验收锚点
- 架构锚点：本版本触及的**分层 / 模块 / 门面 / 契约 / API**（范围声明，非设计论证）
- 功能验收标准：怎么验证、通过标准
- 架构验收标准：模块独立、性能、兼容性等度量约束
- DoD：交付 checklist（确认类）

**300-design.md** — 怎么设计
- 架构背景与目标：设计动机、上一版本基线、影响范围
- TF 划分与契约：每个 TF 的输入/输出/依赖/边界（契约规范见 `docs/06-contract-based-dev.md` §2.2）
- 流间数据流：执行顺序、串并行关系、编排者
- 关键决策：备选方案、选择理由、影响
- 继承关系：本版本对现有模块/流的变更
- 跨 TF 状态机：多 TF 协作的状态跃迁定义
- 测试策略：每个 TF 的测试级别与关键场景

**400-build.md** — 怎么实现、怎么交付
- 通用约束：数据 Schema、API 契约、异常策略
- 每个 TF 的实现详情：目标 → 步骤拆解 → 函数签名 → 伪代码 → 输入输出 → 异常边界
- 风险与缓解：风险列表 + 缓解措施
- 状态机/时序图：跨模块交互流程
- 执行顺序矩阵：序号 → TF → 备注 + 执行顺序说明（先做/可并行/必须串行）

### 2.2 交付环节与排程

每个工作包除「领域」（dev / product / marketing / biz / qa / goal）外，还需标注**环节**——处于交付流水线的哪一段。环节的完整定义、常用环节及所属类别，见 `dm-schedule` skill 的「核心概念」环节↔类别表（**唯一权威来源**），此处不重复维护。

排程遵循以下规则：

1. 市场验证环节（营销/调研）排最前，定义本版本要证明的假设。
2. dev / qa 工作包必须排在对应的市场验证环节之后。
3. qa 工作包必须排在所验收 dev 工作包的「部署 + 联调」环节之后。
4. **dev 工作包完成定义 = 代码 + 部署 + 联调**。部署与联调属于 dev，不属于 qa；qa 只验收「已部署 + 已联调」的功能。
5. schedule 按「环节位置 + 跨领域依赖」排序，而非纯凭经验。

## 3. 以 Transaction Flow 为主轴的设计原则

### 3.1 基本定义

Transaction Flow 是版本内可独立描述、可独立验证的一段业务流或交付流。例如：

- TF1：初始化与前置准备
- TF2：核心处理与转换
- TF3：结果落库与对外输出

Transaction Flow 不是章节编号，而是业务流单元。编号要稳定，名称要表达业务语义。

补充规则：

- TF 编号在同一版本迭代期间必须保持稳定，不得随意重排或重命名。
- 若某个 TF 后续确认废弃，应保留原编号并标记为 `[DEPRECATED]`，避免文档、任务和实现引用失配。

### 3.2 两层设计如何对齐

```
1. 300-design 先定义每个 Transaction Flow 的目标、边界、输入输出和依赖关系
2. 400-build 再展开同一个 Transaction Flow 内部的具体步骤、接口、异常处理，末尾按执行顺序排列执行顺序矩阵
```

### 3.3 分层收益

| | 300-design | 400-build |
|------|:---:|:---:|
| **关注粒度** | Transaction Flow 级别 | 流内步骤级别 |
| **迭代频率** | 低，更多改业务边界 | 高，更多改实现细节 |
| **审核方式** | 人审业务流是否合理 | 人审实现是否完整可落地 |
| **复用价值** | 适合做版本总览和评审 | 适合直接指导编码 |

### 3.4 内容边界

**300-design.md** 包含：
- Transaction Flow 的名称、目标、范围
- 各流之间的先后顺序与依赖关系
- 每个流的输入、输出、成功条件
- 关键架构决策及理由（为什么这样串联）
- 与上一版本或现有能力的继承/变更关系
- **跨 TF 状态机**：当多个 TF 通过状态跃迁协作时，在此定义状态、跃迁条件及各 TF 在状态机中的角色
- **测试策略**：每个 TF 的测试级别（单元/集成/E2E/手工）、关键测试场景、测试环境依赖

**300-design.md 不包含**：
- 函数签名
- 具体 API 参数列表
- 伪代码
- 具体异常回退细节
- 单 TF 内部的状态机（应放在 400-build.md）
- 具体测试用例（策略层级即可，用例细节在 build 中展开）

**200-spec.md** 不包含：
- 输入、输出、依赖关系的详细设计
- 伪代码
- 具体异常回退细节
- 分层依赖方向的论证、模块内部设计、Facade 内部实现（属 300-design.md）
- 实现任务清单 / 工作包（属 400-build.md 与 500-schedule.md）

**200-spec.md** 仅保留业务级别信息：
- 本版本业务目标
- Transaction Flow 的清单与业务目标
- **架构锚点**：本版本触及哪些**分层 / 模块 / 门面 / 契约 / API** —— 只登记「动到哪里」，
  不解释「为什么这样设计」（论证属 `300-design.md`；五维术语权威见 `dm-arch-design` / `docs/09`）
- 功能验收标准
- 架构验收标准（面向业务可见结果）
- DoD

### 3.4.1 防腐（Guardrails）三文档分工

| 文档 | 回答 | 载体 |
|------|------|------|
| 200-spec | 为什么防 / 防什么 | §3 硬约束列 + §3.1 禁止与不做 |
| 300-design | 用什么物理结构防 | §2.1 TF 防腐矩阵（类型 / 错误域 / 物理路径） |
| 400-build | 怎么验证防住了 | §1.4 `GUARD-0x` 表 + §6 矩阵 `guard` 列 + 自检行 |

- 编号：`GUARD-01`…（沿用 `docs/06` §2.6 的域-序号体系）—— **与契约层级 L1 / L2 / L3 无关**
- 200 的模块清单 = 版本级**范围**（防蔓延）；300 的模块（物理路径）= 每 TF **归属**（防越界）
- 400 自检只写命令，规范指针到 `dm-contract-gate`，不重定义

**400-build.md** 包含：
- 每个 Transaction Flow 内部的步骤拆解
- 每一步对应的函数签名、入参、返回值、调用时机
- 数据结构 / Schema 定义
- API 调用顺序与前置条件
- 边界情况与异常路径策略
- 若 Transaction Flow 内部涉及复杂异步状态或交互流程，必须补充文本状态机或时序图（Sequence Diagram）

### 3.5 测试职责分层（指针）

### 6.1 执行顺序矩阵填充规则

`400-build.md` §6 是前文设计的执行视图，只承载 **顺序、环节、依赖约束与验收约束（guard）**。工作内容、工时、状态不在此表维护，统一由 `500-schedule.md` 承载（dev 工作包以 TF 为原子单位，见 §2；环节定义见 §2.2）。

| 列 | 来源 | 提取方式 |
|----|------|----------|
| **序号** | — | 按推荐执行顺序从 1 递增 |
| **环节** | §2.2 交付流水线 | 该行所属环节（开发 / 部署 / 联调 / 测试 / 发布 …）。dev TF 的矩阵须含「代码 + 部署 + 联调」 |
| **TF** | `300-design.md` §2 | TF 编号（TF1 / TF2 / …）。收尾任务填"—" |
| **guard** | §1.4 | 该行须通过的防腐契约编号（`GUARD-01,03`…） |
| **备注** | `300-design.md` §3 | 标注前置依赖、并行提示、风险标记等 |

#### 填充步骤

1. 按 `300-design.md` §3 确认的 TF 执行顺序，为每个 TF 添加一行，标注环节
2. 需部署的 dev TF 追加「部署 + 联调」行（归属 dev，不归 qa）
3. 末尾追加固定行："补单测与回归用例" + "本地构建与回归验证"
4. 填写执行顺序说明（推荐先做、可并行、必须串行）

#### 硬约束

- 矩阵中的每个 TF 必须能在上方 TF 详细设计中找到对应章节
- 执行顺序必须与 `300-design.md` §3 的 TF 依赖关系一致
- 环节顺序须与 §2.2 交付流水线一致（部署 → 联调 → 测试）
- Phase 1 结束时执行顺序矩阵不得留空白行
- 任务简述、预估工时、状态只写 `500-schedule.md`，此处不重复维护
- `guard` 列的每个编号须能在 §1.4 找到对应行

## 7. 模板目录

为了让规范可直接落地，建议为每个版本目录维护对应模板：

```
templates/versions/vX.Y-<slug>/
├── 200-spec.md
├── 300-design.md
├── 400-build.md
└── 500-schedule.md
```

模板用途：

- `500-schedule.md` 模板用于快速起草版本工作包排程。
- `200-spec.md` 模板用于快速起草版本交付范围、架构锚点与验收标准。
- `300-design.md` 模板用于快速起草 Transaction Flow 划分与流转关系。
- `400-build.md` 模板用于快速起草伪代码、状态机、Schema、边界处理 + 执行顺序矩阵。

模板与正式文档必须保持字段和章节结构一致，避免出现"规范更新了、模板没跟上"的漂移。

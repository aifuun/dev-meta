# dm-schedule

## 概述

版本排程 skill，为 Roadmap 版本生成按执行优先级排序的扁平工作包列表，供调度与对账。面向 solo 开发者，定位为战术级 backlog。

## 触发

- "排程"
- "安排版本工作"
- "生成工作包"
- "为 v1.0 做排程"

## 核心概念

排程基于两个正交维度构造工作包：**领域**（谁负责）与**环节**（何时做）。

### 领域与工作包 ID

工作包 ID 格式：`v<X.Y>-<domain>-<NN>`

版本号作命名空间在前，域在后，保证 ID 在 commit / log / Issue 中无需额外上下文即可定位版本。

| 领域 | 范围 |
|------|------|
| `dev` | 开发与架构 |
| `product` | 产品与 UI 设计 |
| `marketing` | 市场营销与推广 |
| `biz` | 商业化与变现 |
| `qa` | 测试走查 |
| `goal` | 版本里程碑目标 |

### 交付环节（验证环节）

每个工作包还需标注**环节**——处于交付流水线的哪一段：

```
调研 → 设计 → 开发 → 构建 → 部署 → 联调 → 测试 → 发布
```

> **环节 ↔ 类别的唯一权威映射**：`02-version-rules.md` §2.2、`400-build.md` 执行顺序矩阵、`dm-plan-ver` 均遵循本表。每环节选一个**主导类别**（主责），个别环节含次要辅助类别。修改环节或类别时优先改本表。

| 环节 | 主导类别 | 流水线位置 | 辅助类别 | 示例工作内容 |
|------|---------|-----------|---------|-------------|
| 调研 | marketing | 最前 | — | 用户访谈、痛点验证、竞品分析 |
| 定位 | marketing | 前段 | — | 目标人群、价值主张、市场定位 |
| 设计 | product | 前段 | dev | UI 设计、交互原型、视觉规范、架构设计 |
| 规格 | product | 前段 | — | PRD、需求规格、验收标准定义 |
| 开发 | dev | 中段 | — | 按 TF 实现代码（完成定义 = 代码+部署+联调） |
| 构建 | dev | 中段 | — | 本地构建、打包、编译 |
| 部署 | dev | 中段 | — | 函数/服务发布到目标环境 |
| 联调 | dev | 中段 | — | 前端 ↔ 已部署服务打通、修 bug |
| 测试 | qa | 后段 | dev | qa 验收已部署功能；dev 补单测与回归 |
| 发布 | marketing | 最末 | biz / dev | 正式发布、商店提交、推广、变现 |

> 环节决定「何时做」，主导类别决定「谁负责」。辅助类别仅在协作场景使用（如「设计」由 product 主导、dev 辅助实现细节；「测试」由 qa 主导、dev 辅助补单测）。

### dev 工作包规则

#### 粒度：以 TF 为原子单位

dev 工作包必须以 **Transaction Flow (TF)** 为单位组织，每个 TF 是不可分割的原子工作包：

| 粒度 | 允许？ |
|------|--------|
| TF 级（一个 dev 工作包 = 一个 TF） | ✅ 必须 |
| 步骤级（如"创建 yaml"、"配置 webpack"） | ❌ 禁止 |

- 每个 dev 工作包 = 一个 TF，工作内容栏写 TF 名称 + 一行摘要 + `详见 400-build §N`
- TF 内部的具体步骤由 `400-build.md` 承载，不在 schedule 表格中展开
- 工时取 `400-build.md` 中该 TF 的总和
- 非 dev 工作包（product / marketing / biz / qa / goal）不受此限制

#### 完成定义：代码 + 部署 + 联调

dev 工作包**完成定义** = **代码 + 部署 + 联调**，三者缺一不可：

| 交付物 | 内容 | 验收信号 |
|--------|------|---------|
| 代码 | 按 400-build 实现 TF 逻辑 | 单测/回归通过 |
| 部署 | 函数/服务发布到目标环境 | 部署成功可访问 |
| 联调 | 前端 ↔ 已部署服务打通 | 端到端链路验证通过 |

- **部署与联调属于 dev，不属于 qa**。qa 只验收「已部署 + 已联调」的功能，不负责让它跑起来。
- schedule 中必须为需要部署的 dev 工作包显式安排「部署 + 联调」行，不得隐含在 qa 里。

## 排程规则

基于环节位置与跨领域依赖排序，而非纯凭经验：

1. **市场验证环节（营销/调研）排最前**，定义本版本要证明的假设。
2. **dev / qa 工作包排在对应的市场验证环节之后**（假设确认后再开发）。
3. **qa 工作包排在所验收 dev 工作包的「部署 + 联调」环节之后**。
4. 每版本强制覆盖多个领域（dev + product + marketing + biz + qa）。

## 执行流程

### 1. 收集上下文

询问用户：版本号、上线卡点、量化目标、已知交付物。

### 2. 生成工作包列表

创建 `docs/versions/vX.Y-<slug>/500-schedule.md`。按优先级顺序填充，确保跨领域覆盖：

1. **基础搭建** — 仓库脚手架、设计 token、品牌资产
2. **核心 UX** — 主用户流程
3. **集成对接** — 第三方服务、支付、部署
4. **质量走查** — 跨设备测试、bug 修复
5. **正式发布** — 商店提交、营销推广

每行工作包须标注「环节」，且市场验证环节排最前（见「排程规则」）。

### 3. 定义红线

四铁律默认保留，除非用户显式覆盖：

1. **市场任务不完成，严禁写新代码**：若本周的市场/用户验证任务未完成，严禁开启新代码开发。
2. **2 小时停损原则**：任何非核心 UI / 动效 / 重构折腾超过 2 小时无果，立刻降级为基础实现或暂扣。
3. **闭环高于完美**：优先保证主路径通畅（Happy Path），边缘异常留待下一版本处理。
4. **每周日强制对账**：对照本表打勾，超时 Task 通过砍掉后续非核心 `vX.X-dev-*` 工作包来补偿时间。TF 内部步骤可重排优先级，但 TF 本身不可分割。

### 4. 确认保存

显示排程供审查。确认后保存到 `docs/versions/vX.Y-<slug>/500-schedule.md`。

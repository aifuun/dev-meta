# Version Rules — 版本目录文件规范

本规范定义版本体系的四个层级（**Milestone → Epoch → 版本 → Step**）、版本目录下的标准文件结构、职责分工与写作方式。

> **唯一权威**：本文是版本规则（目录结构、四件套结构、Step 施工流、版本粒度、编号规则）的唯一权威。
> 分支 / commit / PR 规则见 `docs/03-git-flow-rules.md`；契约层级见 `docs/06-contract-based-dev.md`；AI 执行粒度见 `docs/08-small-batch-iteration.md`。本文只引用，不重定义。

---

## 1. 目录结构

```
docs/versions/<版本号>-<slug>/
├── 200-spec.md        # 考什么：交付目标与验收标准
├── 300-design.md      # 为什么这么设计：架构、数据流、算法、决策
├── 400-build.md       # 怎么造：Step 0–7 施工流 + GUARD 防腐
└── 500-schedule.md    # 排程：工作包列表与执行顺序
```

### 创建顺序

> 版本级四文档按以下顺序创建，每步都是下一步的前置条件：

| 顺序 | 文档 | 回答的问题 | 前置依赖 |
|------|------|-----------|----------|
| 1 | `200-spec.md` | 交付什么？怎样算完成？ | — |
| 2 | `300-design.md` | 技术上怎么设计？ | spec |
| 3 | `400-build.md` | 分几步施工？怎么验证防住了？ | design |
| 4 | `500-schedule.md` | 谁在什么时候做什么？ | build |

## 2. 各文件职责

| 文件 | 受众 | 回答的问题 | 关键内容 |
|------|------|-----------|---------|
| `200-spec.md` | PM / QA / Dev | 这个版本交付什么？怎样算完成？ | 核心业务场景、**架构锚点（分层/模块/门面/契约/API）**、功能验收标准、架构验收标准、明确不做、DoD |
| `300-design.md` | 架构师 / Dev | 技术上怎么设计？ | 全局架构与分层、防腐设计（类型/错误域/物理路径）、数据流与状态机、核心算法方案、关键决策（ADR）、继承关系、测试策略 |
| `400-build.md` | Dev | 分几步施工？怎么验证防住了？ | **Step 0–7 施工清单**（含跳过理由）、函数签名 / Schema / 异常策略、`GUARD-0x` 防腐表、风险与缓解 |
| `500-schedule.md` | PM / Dev | 谁在什么时候做什么？ | 工作包列表（跨领域）、类别、环节、难度、预估工时、验收标准、状态。dev 工作包以 **Step** 为原子单位，完成定义含代码+部署+联调 |

### 2.1 四件套分工总览

```
200-spec     → 考什么（业务与验收）
300-design   → 为什么这么设计（架构决策）
400-build    → 怎么造（Step 0–7 施工流 + GUARD 防腐）  ← 唯一承载 Step 的文档
500-schedule → 排程（谁何时做什么）
```

**200-spec.md** — 干什么、怎样算完
- 核心业务场景：一句话能讲清的**单一**场景
- 架构锚点：分层 / 模块 / 门面 / 契约 / API（范围声明，非设计论证）
- 功能验收标准、架构验收标准
- 明确不做（Out of Scope）
- DoD：确认类 checklist

**300-design.md** — 技术上怎么设计
- 架构背景与目标
- 架构与分层（含防腐设计：类型 / 错误域边界、模块物理路径与工程登记）
- 数据流与状态机（含跨模块状态跃迁）
- 核心算法方案
- 关键决策（ADR）
- 与现有版本的继承关系
- 测试策略

**400-build.md** — 分几步造
- 通用约束（Schema / API 契约 / 异常 / 防腐契约）
- **Step 0–7 施工清单**（唯一拆分层级）
- 每个**执行**的 Step 的实现明细
- 风险与缓解、自检与验收

### 2.2 交付环节与排程

每个工作包除「领域」（dev / product / marketing / biz / qa / goal）外，还需标注**环节**——处于交付流水线的哪一段。环节的完整定义、常用环节及所属类别，见 `dm-schedule` skill 的「核心概念」环节↔类别表（**唯一权威来源**），此处不重复维护。

> ⚠️ **三条正交的轴，不得混用**：
> **Step**（`400-build`）= 技术施工工序，回答「这件事分几步造」；
> **环节**（`500-schedule`）= 交付流水线位置，回答「谁在什么时候做、什么时候能验收」；
> **Batch**（AI 执行粒度，见 `docs/08-small-batch-iteration.md`）= 回答「**AI 一步能迈多大**」—— 与上两者正交，**不由本规范定义**。

排程遵循以下规则：

1. 市场验证环节（营销/调研）排最前，定义本版本要证明的假设。
2. dev / qa 工作包必须排在对应的市场验证环节之后。
3. qa 工作包必须排在所验收 dev 工作包的「部署 + 联调」环节之后。
4. **dev 工作包完成定义 = 代码 + 部署 + 联调**。部署与联调属于 dev，不属于 qa；qa 只验收「已部署 + 已联调」的功能。
5. schedule 按「环节位置 + 跨领域依赖」排序，而非纯凭经验。

## 3. 版本体系与粒度红线

### 3.1 四层结构

```
Milestone（业务目标）                    → 05_ROADMAP §1
  └── Epoch（版本组 = 一个完整 feature）  → 05_ROADMAP §2
        └── 版本（一个核心业务场景）      → 本规范 §4–§6 四件套
              └── Step 0–7（施工流）      → 400-build §2
```

| 层级 | 回答 | 载体 | 规划者 |
|------|------|------|--------|
| Milestone | 业务上要达到什么 | `05_ROADMAP_AND_COMPLIANCE.md` §1 | `dm-plan-roadmap` |
| Epoch | 哪几个版本共同交付一个完整 feature | 同上 §2 | `dm-plan-roadmap` |
| 版本 | 这一版做哪个**单一**核心场景 | 四件套 | `dm-plan-ver` |
| Step | 这件事分几步造 | `400-build` §2 | `dm-plan-ver` → `dm-dev-step` |

### 3.2 版本粒度红线（强制）

> 一个版本**只承载单一核心业务场景**。若需拆出多个独立业务流，说明版本过大，**必须拆为多个版本**。

**不使用 TF**：版本已足够小，不再在版本内划分业务流。施工层级由固定的 `Step 0–7` 承担。

粒度判据**分两次执行**：

| 阶段 | 判据 | 性质 |
|------|------|------|
| 切版本时（`dm-plan-roadmap`） | 预期 S4 / S5 **各只出现一次** | 人工预估 |
| `400-build` 完成后（`dm-plan-ver`） | S4 / S5 **实际出现次数 = 1** | **硬判定**（可机械计数） |

辅助判据（人工确认，**不作硬门禁**）：

- 核心业务场景能用**一句话**写清
- 无需「版本内再分阶段」才能讲清
- 预计生命周期 1–3 天（**经验参考值**，重构版本天然更长）

**实证失败的处理**：`400-build` 写完后若 S4 / S5 出现多于一次 → 版本该拆 →
**退回 `dm-plan-roadmap` 重切**，**不得在版本内自行加层级**（不得因此引入 TF）。

### 3.3 版本编号规则

**双轴编号**：`v` 轴承载功能，`r` 轴承载重构，**互不混号**。

```
v20  v21  v22  …    功能轴（feature）：新能力、新界面、新流程
r1   r2   r3   …    重构轴（refactor）：纯重构、技术债、架构收口
```

**Epoch 号段分配**：

- 每个 Epoch 分配一段连续号段，**群内连续、群间留白 10 号**
- 例：Epoch A = `v20`–`v29`、Epoch B = `v30`–`v39`、Epoch C = `v40`–`v49`
- 同一 Epoch 内已用 `v30`、`v31`，下一个新版本用 `v32`；**不得插入 `v30.5` 之类的小数号**

**为何留白**：避免「中途插入一个版本导致后续多个版本级联顺延」——该问题在实际项目中已发生过（`mvp-v7` 插入导致其后 6 个版本顺延）。

**版本目录名**：`docs/versions/<版本号>-<slug>/`，如 `v30-main-app-loop`、`r3-image-pipeline`。

### 3.4 内容边界

**200-spec.md 包含**：
- 核心业务场景（一句话）
- 架构锚点（范围声明）
- 功能验收标准、架构验收标准
- 明确不做
- DoD

**200-spec.md 不包含**：
- 输入、输出、依赖关系的详细设计
- 伪代码
- 具体异常回退细节
- 分层依赖方向的论证、模块内部设计、Facade 内部实现（属 300-design.md）
- **任何 TF / Step 章节**（属 400-build.md）
- 实现任务清单 / 工作包（属 400-build.md 与 500-schedule.md）

**300-design.md 包含**：
- 架构目标、上一版本基线、影响范围
- 全局架构与分层落位
- 防腐设计：类型 / 错误域边界、模块物理路径与工程登记
- 数据流与状态跃迁（含跨模块状态机）
- 核心算法方案
- 关键决策（ADR）及理由
- 与现有版本 / 能力的继承与变更关系
- 测试策略（每个关注点的测试级别、关键场景、环境依赖）

**300-design.md 不包含**：
- 函数签名、具体 API 参数列表、伪代码
- 具体异常回退细节
- **任何 TF / Step 章节**（属 400-build.md）
- 具体测试用例（策略层级即可）

**400-build.md 包含**：
- 通用约束（数据 Schema / API 契约 / 异常与边界 / 防腐契约）
- **Step 0–7 施工清单**（唯一拆分层级，含跳过声明）
- 每个执行 Step 的步骤拆解、函数签名、入参/返回值/调用时机、边界与异常策略
- 若某 Step 涉及复杂异步状态或跨端交互，补充文本状态机或时序图

### 3.5 防腐（Guardrails）三文档分工

| 文档 | 回答 | 载体 |
|------|------|------|
| 200-spec | 为什么防 / 防什么 | 架构锚点的硬约束 + 明确不做 |
| 300-design | 用什么物理结构防 | 防腐设计（类型 / 错误域边界 + 模块物理路径） |
| 400-build | 怎么验证防住了 | §1.4 `GUARD-0x` 表 + Step 清单 `guard` 列 + 自检命令 |

- 编号：`GUARD-01`…（沿用 `docs/06` §4 的域-序号体系）—— **与契约层级 L1 / L2 / L3 无关**
- 命名空间互斥：`Step`（工序）/ `GUARD-0x`（防腐）/ `L1-L3`（契约层级）/ `<DOMAIN>-NNN`（契约 ID），四者含义唯一，不得交叉；**契约域前缀的命名规则与保留空间见 `docs/06` §6.3**
- 400 自检只写命令，规范指针到 `dm-contract-gate`，不重定义

### 3.6 测试职责分层（指针）

> **唯一权威见 `docs/06-contract-based-dev.md` §10（测试职责分层）**。本处以指针形式保留，避免与契约式开发文档重复定义。

### 3.7 编号体系沿革（2026-09）

**TF（Transaction Flow）已由 Step 取代**：

| 时期 | 版本内拆分方式 | 载体 |
|------|--------------|------|
| 2026-09 之前 | Transaction Flow（业务流编号 `TF1` / `TF2` …） | `200-spec` TF 清单 + `300-design` TF 划分 |
| **2026-09 起** | **Step 0–7**（固定工序，版本内不再划分业务流） | `400-build` Step 施工清单 |

- **历史版本不迁移**：2026-09 之前创建的版本，其 `200-spec` / `300-design` 仍保留 TF 章节，属历史事实，**不得改写**
- **新版本一律使用 Step**；`200-spec` / `300-design` 不得出现任何 TF 或 Step 章节（见 §8 反模式）
- 结构检查（§8）须**豁免历史版本**：以版本创建时间为界，或由版本目录内 `@legacy` 标记豁免

### 6.1 Step 清单填充规则

`400-build.md` §2 是唯一承载施工拆分的表。工作内容、工时、状态不在此表维护，统一由 `500-schedule.md` 承载（dev 工作包以 **Step** 为原子单位，见 §2；环节定义见 §2.2）。

| 列 | 来源 | 提取方式 |
|----|------|----------|
| **Step** | 本规范 §6.2 | `S0`–`S7`，固定顺序，不得增删 |
| **名称** | 本规范 §6.2 | 固定（见下表） |
| **执行态** | — | 执行 / `⏭️ SKIPPED`（跳过须写理由；**进度状态**不在此维护，属 `500-schedule`） |
| **环节** | §2.2 交付流水线 | 该 Step 所属环节（开发 / 部署 / 联调 / 测试 / 发布 …） |
| **guard** | §1.4 | 该 Step 须通过的防腐契约编号（`GUARD-01,03`…） |
| **交付物 / 跳过理由** | — | 交付物清单；跳过时写「跳过：<理由>」 |

#### 填充步骤

1. 写入固定 8 行（S0–S7）
2. 逐行判定**执行态**：必做步填「执行」；条件步无对应场景时填 `⏭️ SKIPPED` + 理由
3. 为执行的行标注环节与须通过的 `guard`
4. 在 §3 为每个执行 Step 展开明细

#### 硬约束

- 固定的 8 行**不得增删**（不得因为版本小就删掉 S6 之类的必做步）
- **必做步**（S0 / S1 / S6 / S7）不得标记为 SKIPPED
- 条件步跳过必须写理由，格式固定为「跳过：<理由>」
- `guard` 列的每个编号须能在 §1.4 找到对应行
- **S4 / S5 各只出现一次**（粒度红线的硬判据，见 §3.2）；出现多于一次须退回 `dm-plan-roadmap` 重切
- 任务简述、预估工时、**进度状态**（⬜ / 🔄 / ✅）只写 `500-schedule.md`；本表的「**执行态**」（执行 / SKIPPED）是设计决定，与进度状态是两回事
- **契约结构 lint 关版本前必跑且全绿**（`docs/06` §8.4）：`python3 <contract-lint>/contract_lint.py --contracts-dir <契约目录>`；与 `GUARD-0x`、单测并列，属收口前门禁，未绿不得进入 S7 收口

### 6.2 Step 0–7 定义

| Step | 名称 | 职责 | 必做性 |
|------|------|------|--------|
| **S0** | Scaffold & Clean | 脚手架建设与历史基线清理（分支、遗留、工程配置）。不改生产代码 | 必做 |
| **S1** | Contract & ADR | 架构决策记录（ADR）、冻结接口签名与下游契约；新接口可先落 `[PLANNED]` 占位 | 必做 |
| **S2** | Core & Prototype | 隔离环境中抽离 Pure Model / 核心算法，写 Harness 跑出真实数据。**只造引擎，不装车**（禁止改主 UI） | 条件：有核心算法或数据量化需求 |
| **S3** | Standard Finalization | 把 S2 实测数据回填契约，留 1.5–2.5× 余量，设定门禁阈值；契约 `[PLANNED]` → `[CURRENT]`（状态生命周期见 `docs/06` §4.2） | 条件：S2 产出了实测数据 |
| **S4** | Ingress Migration | 输入 / 预览侧生产链路接入新引擎（ViewModel → UI）；**接入时同时接好轨迹观测点**（`docs/07` §3.2） | 条件：存在前端/预览链路 |
| **S5** | Egress Migration | 输出 / 保存 / 导出侧接入新引擎，收敛导出管道与安全防线；**接入时同时接好轨迹观测点**（`docs/07` §3.2） | 条件：存在导出/保存链路 |
| **S6** | Guards & Tests | 静态防腐守卫（`GUARD-0x`）+ 契约结构 lint（`docs/06` §8.4）+ **轨迹资产核对与验证（必做）** + 全量单测与回归 | 必做 |
| **S7** | Verification & Close | 真机 / 生产环境验收，**关版本前必跑契约结构 lint 全绿**（`docs/06` §8.4）、合并（保留历史，禁 squash）、打 Tag、收口 | 必做 |

> 📌 **轨迹验证（`S6` 必做，**非条件式**）**：核对轨迹目录与实现一致、判读表无模糊行、临时项未超棘轮；本版有轨迹变更时，须在**完整逻辑链路**（集成 / E2E）上验证「一次命中」，**不得以单元测试代替**（见 `docs/07` §3.2）。尚未启用轨迹的项目，须在 `S0` 显式登记本项为待办，不得静默略过。

> 📌 **UI 变更纪律（`S4` / `S5` 涉及视图改动时强制）**：
> ① **改动须可局部回滚** —— 单个 UI 变更不得与样式重构混入同一 commit；
> ② **不得顺手改 Design Token / 全局样式**（颜色 / 字号 / 间距 / 圆角 / 动效）—— 确需改动须单列 Step 并写明影响面；
> ③ **视觉真值源是 Design Token**，AI 不得绕过 token 直写魔数（见 `docs/09` §5 第 8 条）；
> ④ UI 改动**不写单测**，但须附**可复查对照物**（Preview 截图 / 前后对比 / 真机验证记录）—— 见 `docs/08` §2.2 第 5 条。

#### Step 内部的演进顺序（自底向上，强制）

每个涉及代码改动的 Step 内部，必须遵循自底向上：

```
1. Pure Model / Domain    底层算法、纯数据结构，无 UI 依赖
2. Use Case / Application 用例门面，隔离底层细节，防止 UI 越级调用
3. ViewModel / State      状态流水线（防抖、异步并发、状态机）
4. UI / Presentation      仅数据绑定与视图合成，不含计算逻辑
```

> 详见 `docs/09-ai-architecture-guide.md`。

### 6.3 数据驱动阈值（强制）

性能、精度、误差类门禁指标，**必须由 S2 的 Harness 跑出真实物理数据后定案**（S3），严禁凭空预设。
S3 回填的阈值须写入契约并配可执行断言（`GUARD-0x` 或契约不变性）。

## 7. 模板目录

为了让规范可直接落地，建议为每个版本目录维护对应模板：

```
templates/versions/vX.Y-<slug>/
├── 200-spec.md
├── 300-design.md
├── 400-build.md
└── 500-schedule.md
```

模板用途：

- `200-spec.md` 模板用于快速起草版本交付范围、架构锚点与验收标准。
- `300-design.md` 模板用于快速起草架构与分层、数据流与状态机、核心算法与关键决策。
- `400-build.md` 模板用于快速起草 Step 0–7 施工清单、明细、防腐契约与自检。
- `500-schedule.md` 模板用于快速起草版本工作包排程。

模板与正式文档必须保持字段和章节结构一致，避免出现"规范更新了、模板没跟上"的漂移。

# dm-plan-roadmap

## 概述

版本路线规划 skill。负责**跨版本**的规划：Milestone 划分、Epoch（版本组）划分、**版本粒度红线校验**与**编号分配**。
产出并维护 `docs/05_ROADMAP_AND_COMPLIANCE.md` 的 §1 Milestone 与 §2 Epoch Plan。

## 职责边界

| 职责 | 归属 |
|------|------|
| Milestone / Epoch 划分、编号分配 | ✅ 本 skill |
| **版本粒度红线校验**（预估 + 接收实证回报） | ✅ 本 skill |
| 生成 `05_ROADMAP` 骨架（一次性） | 委托 `dm-init-docs` |
| 单个版本的四件套（200/300/400/500） | 委托 `dm-plan-ver` |
| 单个版本的工作包排程 | 委托 `dm-schedule` |
| 编号 / 粒度**规则的文本** | ❌ `docs/02-version-rules.md` §3（本 skill 只执行，不重定义） |

## 触发

- "规划路线图"
- "切版本" / "版本怎么切"
- "划分 Epoch" / "这个版本组怎么排"
- "这个版本是不是太大了"
- 收到 `dm-plan-ver` 的**粒度实证失败**回报

## 核心概念

### 四层结构

```
Milestone（业务目标）                    → 05_ROADMAP §1
  └── Epoch（版本组 = 一个完整 feature）  → 05_ROADMAP §2
        └── 版本（一个核心业务场景）      → dm-plan-ver 四件套
              └── Step 0–7（施工流）      → 400-build
```

**不要**在版本内再引入拆分层级（如 TF）——那是版本过大的信号，应拆版本，不是加层级。

### 版本粒度红线（本 skill 的核心职责）

> 一个版本**只承载单一核心业务场景**。若需拆出多个独立业务流，说明版本过大，**拆为多个版本**。

**校验分两次，不可合并**：

| 阶段 | 判据 | 性质 | 谁执行 |
|------|------|------|--------|
| 切版本时 | **预期** S4 / S5 各只出现一次 | 人工预估 | 本 skill |
| `400-build` 完成后 | **实际** S4 / S5 出现次数 = 1 | **硬判定**（可机械计数） | `dm-plan-ver` |

辅助判据（人工确认，**不作硬门禁**）：核心场景能一句话写清；无需「版本内再分阶段」；预计生命周期 1–3 天（**经验参考值**，重构版本天然更长）。

**实证失败的回环**：`dm-plan-ver` 实证发现 S4 / S5 多于一次 →
**退回本 skill 重切版本**，不得在版本内自行加层级。

### 编号规则（详见 `docs/02` §3.3）

- **双轴**：`v` 轴承载功能（feature），`r` 轴承载重构（refactor），**互不混号**
- **Epoch 号段**：每个 Epoch 分配一段连续号段，**群内连续、群间留白 10 号**
  - 例：Epoch A = `v20`–`v29`、Epoch B = `v30`–`v39`
  - 同一 Epoch 内已用 `v30`、`v31` → 下一个新版本用 `v32`；**不得插入 `v30.5`**
- **为何留白**：避免「中途插入一个版本导致后续多个版本级联顺延」

### Epoch 划分原则

- 一个 Epoch = 若干版本共同交付**一个完整 feature**
- Epoch 内版本必须有明确的**前后依赖**（填「依赖」列），且构成一条可交付路径
- Epoch 完成判据 = 其声明的完整 feature 可独立交付（写进「目标」列）

## 执行流程

### 1. 读取现状

```bash
ls docs/versions/                                   # 已有版本目录
grep -n "Epoch" docs/05_ROADMAP_AND_COMPLIANCE.md   # 现有划分
```

检查 `05_ROADMAP_AND_COMPLIANCE.md` 是否存在；缺失则提示先跑 `dm-init-docs`。

### 2. 收集意图（grill）

按需向用户确认 **3–5 个决定性决策点**（不重复文档已有内容）：

- 本轮要交付的完整 feature 是什么？（→ 一个 Epoch）
- 它必须拆成几个版本？每个版本的**单一核心场景**是什么？
- 版本之间的依赖顺序？
- 是否有纯重构需求需要走 `r` 轴？

### 3. 输出「版本粒度合规性评估报告」

对**每个**拟新增版本，逐条校验并显式列出：

```markdown
### v33 粒度合规性评估

- [ ] 核心场景能一句话写清：<一句话>
- [ ] 预期 S4（Ingress）只出现一次：<未来 S4 覆盖什么>
- [ ] 预期 S5（Egress）只出现一次：<未来 S5 覆盖什么，或「本版本无导出侧」>
- [ ] 无需「版本内再分阶段」才能讲清
- 参考：预计生命周期 ≈ N 天（经验值，不作门禁）

结论：✅ 合规 / ❌ 过大（→ 拆为 v33 / v34，理由：…）
```

**任一项不通过即不得生成该版本的四件套** —— 先拆版本，再走 `dm-plan-ver`。

### 4. 写入 Epoch Plan

更新 `05_ROADMAP_AND_COMPLIANCE.md` §2 表（含「粒度校验」列）：

| Epoch | 版本 | 目标 | 依赖 | 粒度校验 | 状态 |
|-------|------|------|------|----------|------|
| B | `v30` | … | — | ✅ S4/S5 各一次 | ⬜ |

同时核对 §1 Milestone 与 §2 的对应关系。

### 5. 交棒

- 每个版本的具体范围与验收 → 委托 `dm-plan-ver`（其产出前会跑需求级 / 架构级 grill）
- 版本排程 → 委托 `dm-schedule`
- 技术选型类决策 → 触发 `dm-adr`

## 产出与完成判据

**产出**：
- `docs/05_ROADMAP_AND_COMPLIANCE.md` §1 Milestone + §2 Epoch Plan（含粒度校验列）
- 每个新增版本的「**版本粒度合规性评估报告**」

**完成判据**：

- [ ] 每个新增版本都有合规性评估报告，且**全部通过**
- [ ] Epoch 内版本的依赖顺序成链，无循环
- [ ] 编号遵 `v` / `r` 双轴，号段无冲突、无小数号
- [ ] Epoch 号段群间留白 ≥ 10 号
- [ ] `05_ROADMAP` §2「粒度校验」列已填写
- [ ] 每个版本已明确后续交接给 `dm-plan-ver`

## 使用示例

```
用户: "规划一下 v3x 这一段路线"

AI:  1. 读 docs/05_ROADMAP：Epoch A 已收官（v20–v22），当前应开 Epoch B
     2. 收集意图：
        - 完整 feature？→「主 App 可独立交付」
        - 拆几个版本？→ v30 闭环 / v31 微调 / v32 面板
        - 依赖顺序？→ v30 → v31 → v32
     3. 逐版本出粒度合规性评估：
        v30：核心场景「主 App 选图→打码→保存闭环」✅ 一句话
             预期 S4（选图/预览）一次 ✅   预期 S5（保存/分享）一次 ✅
             → ✅ 合规
        v31：仅「手势微调」✅ → 合规
     4. 写入 05_ROADMAP §2：

        | Epoch | 版本 | 目标 | 依赖 | 粒度校验 | 状态 |
        | B | `v30` | 主 App 闭环 | — | ✅ S4/S5 各一次 | ⬜ |
        | B | `v31` | 手势微调 | v30 | ✅ 无导出侧变更 | ⬜ |
        | B | `v32` | 极简面板 | v30 | ✅ 无导出侧变更 | ⬜ |

     5. 交棒：v30 的具体范围 → 委托 dm-plan-ver

用户: "v30 的 400-build 写完了，但发现有两处独立的预览切线"

AI:  实证失败（S4 出现 2 次）→ 版本过大。
     **退回 dm-plan-roadmap 重切**：拆为 v30（选图链路）+ v30b/v31（第二处切线），
     不得在 v30 内部自行加层级。
```

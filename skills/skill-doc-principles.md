# Skill 文档核心原则

> 本文档定义 dev-meta 仓库 `skills/` 下所有 skill 设计文档的统一组织结构与写作规范。所有 skill 文档（如 `dm-schedule.md`、`dm-plan-ver.md`、`dm-dev-tf.md`、`dm-adr.md`）须遵循本原则，保证结构一致、AI 工具易遍历、概念单一权威。

## 目标

- **结构一致**：所有 skill 用同一套章节骨架，AI 遍历时心智模型统一。
- **概念驱动**：把「概念/规则」提到正文顶层，而不是埋在流程步骤里。
- **单一权威**：跨 skill 共享的概念（如环节↔类别表）只在一处定义，其余引用。
- **边界清晰**：每个 skill 第一眼就能看清「管什么 / 委托什么」。

## 标准章节骨架

所有 skill 文档按以下顺序组织：

```
# <skill 名>

## 概述          一句话：这是什么 skill，产出什么
## 职责边界      本 skill 管什么 / 委托什么（可选，适用于有委托的 skill）
## 触发          用户说哪些话会触发本 skill
## 核心概念      支撑排程/决策的关键概念（概念优先，提升到顶层）
## 执行流程      AI 按步骤操作（核心阶段展开，委托阶段简述）
## 关键规则速查  单一权威规则表，正文不重复
## 资源映射      本 skill 用到的模板/assets/references
## 使用示例      1-3 个端到端示例
```

### 章节职责说明

| 章节 | 职责 | 写作要点 |
|------|------|---------|
| **概述** | 定位 | 一句话说清 skill 的功能与产出，不展开细节 |
| **职责边界** | 边界 | 表格：本 skill 管什么 ✅ / 委托什么（指向目标 skill） |
| **触发** | 触发 | 用户自然语言触发词列表 |
| **核心概念** | 概念 | 把「规则依赖的关键概念」提升为顶层章节；共享概念指向唯一权威处 |
| **执行流程** | 操作 | 核心阶段展开步骤；委托阶段仅一句 + 指向目标 skill |
| **关键规则速查** | 权威 | 唯一的规则汇总表；正文各处规则不得与表重复 |
| **资源映射** | 资源 | 表格列出 assets / references / 模板及来源 |
| **使用示例** | 示例 | 端到端对话示例，帮助 AI 匹配输入→输出模式 |

## 核心原则

### 1. 概念驱动，不流程驱动

- 用户/AI 按「概念」查找（如"环节归谁"），不按流程步骤查。
- 把「核心概念」提升到执行流程**之前**的顶层章节。
- 若某概念是排程/决策的依据，它不应埋在流程子节里。

### 2. 单一权威（Single Source of Truth）

- 跨 skill 共享的概念**只在一处定义**，其余文档**引用**而非重复。
- 示例：`环节↔类别`表定义在 `dm-schedule`「核心概念」中，`02-version-rules.md`、`400-build.md`、`dm-plan-ver` 均引用它。
- 修改共享概念时，**先改权威处**，再同步引用方。

### 3. 职责边界显式化

- 有委托关系的 skill 必须开「职责边界」章节，用表格列明管什么/委托什么。
- 委托阶段在执行流程中仅一句 + 指向目标 skill，不展开。

### 4. 规则表是唯一权威

- 「关键规则速查」表是规则的唯一汇总。
- 正文各处的规则表述必须与表一致，不得出现正文和表重复/冲突。
- 规则表每条标注来源（规范文档或其它 skill）。

### 5. 单一权威 + 自动部署（中文源 → SKILL.md）

- 每个 skill **只有一份权威**：`skills/<skill>.md`（中文源，含 YAML frontmatter `name` / `description`）。
- 部署版 `~/.codebuddy/skills/<skill>/SKILL.md` **由 `pub_local.py --deploy` 从中文源自动生成**，**禁止手工编辑**。
- 不再维护语言双份：中文源即部署内容（AI 可直接执行中文指令），因此**从结构上消除双端漂移**。
- 新增/调整 skill 时：只改中文源 → `python3 pub_local.py --deploy` 生效。
- skill 的 `assets/` 与 `references/` 仍放在 `skills/<skill>/` 目录下，随部署一并同步。

> **历史**：早期采用「中文设计文档 + 英文部署版」双端维护，实践暴露出「两处必漏改一处」的结构性漂移（规则条目缺失、章节缺失、引用已删资源）。已统一为中文单源 + 自动部署。

### 6. 面向 AI 可遍历

- 用清晰的一级/二级标题，便于 AI 定位章节。
- 概念表、规则表用 Markdown 表格（AI 易解析）。
- 示例用代码块（fenced block）包裹，明确输入→输出模式。
- 触发词放在显眼章节，便于 AI 匹配用户意图。

### 7. 决策点显式收敛

- 影响实现/验收的决策点，必须有显式的「AI 提问 → 用户回答 → 沉淀文档」三步，**不依赖 AI 自问自答**。
- 触发时机：在文档产出前（如 `200-spec` 前的需求级、`300-design` 前的架构级、开发概要前的实现级）。
- 问题聚焦 3-5 个**决定性决策点**，不重复文档已有内容，避免流程负担。
- 沉淀规则：决策性回答写入对应文档章节；技术选型类回答触发 `dm-adr` 记录；问答不得留在对话流中丢失。

## 反模式（避免）

| 反模式 | 问题 | 修正 |
|--------|------|------|
| 概念埋在执行流程的深层子节 | AI 找不到概念 | 提升为顶层「核心概念」 |
| 同一概念在多文档重复定义 | 多处漂移，改一处漏一处 | 只在一处定义，其余引用 |
| 规则分散在正文 + 规则表两处 | AI 不知以谁为准 | 规则表唯一权威，正文不重复 |
| 委托 skill 的完整流程展开在父 skill | 重复维护，职责混乱 | 父 skill 仅一句 + 指向目标 |
| 手工编辑部署版 `SKILL.md` | 与中文源漂移，两处必漏改一处 | 部署版由脚本生成，只改中文源 |
| 决策点靠 AI 自问自答，无显式提问 | 隐性假设未收敛，信息不全即产文档 | 决策点显式「提问→回答→沉淀」三步 |

## 部署同步

- 部署版 `SKILL.md` 位于 `~/.codebuddy/skills/<skill>/SKILL.md`，**由 `pub_local.py --deploy` 从中文源自动生成，禁止手工编辑**。
- 修改中文源后执行 `python3 pub_local.py --deploy` 即生效；无需手工同步章节，也不可能漂移。
- 共享 references（如 `version-rules.md`、`git-flow-rules.md`）在 `docs/` 源文档变更后，须重新同步到各 skill 的 references/。

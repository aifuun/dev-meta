# 契约式开发（Contract-Based Dev）

## 1. 概述

定义 dev-meta 中「先定契约、后实现」的统一规范。契约是模块 / 函数间、TF 间、实现与测试间的**可验证约定**，先于编码确立，以降低集成风险、避免「签名写了但行为没人管」。

本文档是契约式开发的**唯一权威**，各模板与 skill 只引用、不重定义。

契约分三层（详见 §2）：

- **L1 接口 / API 契约**（基线级）：模块间调用约定。
- **L2 TF 契约**（设计级）：每个 Transaction Flow 的输入 / 输出 / 依赖 / 边界。
- **L3 关键行为契约**（测试级）：算法 / 隐性契约函数的给定场景预期（given-when-then）。

## 2. 契约三层级

### 2.1 L1 接口 / API 契约（基线级）

- **定义**：模块间调用顺序、前置条件、返回值 / 错误码约定。
- **载体**：`templates/project/docs/03_CONTRACTS_AND_API.md` §2（接口契约模板）；`templates/versions/vX.Y-<slug>/400-build.md` §1.2（版本内模块共用的 API 契约）。
- **时机**：项目初始化阶段，架构基线完成后建立契约基线（见 `docs/01-project-dev-flow.md` §3.3）；每个版本在 400-build 中维护。
- **字段**：接口名 / 方法 / 入参 / 出参 / 错误码 / 调用顺序 / 前置条件 / 返回值约定。

### 2.2 L2 TF 契约（设计级）

- **定义**：每个 Transaction Flow 的输入 / 输出 / 依赖 / 边界。
- **载体**：`docs/02-version-rules.md` 300-design 职责「TF 划分与契约」（落地于 `300-design.md`）。
- **时机**：版本设计阶段（300-design），先于 400-build 实现。
- **字段**：TF 编号 / 名称 / 输入 / 输出 / 依赖（其他 TF 或模块）/ 边界（失败、并发、配额等）。

### 2.3 L3 关键行为契约（测试级）

- **定义**：对算法类 / 有隐性契约（幂等、并发去重、异常分支、降级取舍）的函数，规定「给定场景下的预期行为」（given-when-then）。这是**行为规定**，不是测试实现。
- **载体**：`templates/versions/vX.Y-<slug>/400-build.md` §2.3 / §3.3「关键行为契约」。
- **适用范围**：仅算法类 / 隐性契约函数必填；薄胶水 / CRUD 函数可省略。
- **字段**：函数 / 场景 / 预期（given-when-then）。
- **落地**：由 `dm-dev-tf` 据此生成真实单测。

### 2.4 三层关系与流转

- L1 定模块边界 → L2 定 TF 边界 → L3 定函数行为；**下层契约不得违背上层**。
- 三者共同构成「契约式开发」骨架：先契约、后实现、再测试。

### 2.5 契约质量基线（唯一权威）

契约不仅要「写在哪里」，还要「写到位」。以下维度是**一份合格契约的最低基线**，三层各自按需包含；缺失即视为契约不完整，须在规划 / grill 阶段补齐。

**L1（接口/API）必含维度**
- **错误契约**：错误码枚举、异常分层、是否可重试，显式写入（禁止散落裸 `throw`）。
- **幂等性**：标注接口是否幂等（尤其写操作 / POST），作为重试与并发去重依据。
- **兼容契约**：变更遵循「加字段不删、不改语义」；破坏性变更须版本化（版本号 / 路径）。
- **超时与限流**：明确 SLA、超时、限流（429）行为。

**L2（TF）必含维度**
- **失败语义**：边界不只用词（失败 / 并发 / 配额），须写明失败后的状态与可恢复性。
- **前置 / 后置条件**：用 requires / ensures 风格写明函数级契约（Design by Contract）。
- **依赖方向**：TF 依赖图单向无环，避免循环契约。

**L3（行为）必含维度**
- **不变量（Invariant）**：标注跨调用的状态不变量（如缓存命中下限、队列非空不可关闭）。
- **契约变更即测试**：行为契约变更须驱动回归测试重跑（见 §3 落地）。

**跨层 Clean Code 编码约定（契约视角）**
- 命名即契约：标识符表达意图（如 `fetchUserOrNull` 暗示可能为空，而非抛异常）；布尔参数用枚举而非裸 `bool`。
- 失败透明：不为「看起来干净」吞掉错误（no empty catch），错误沿契约边界上浮；错误 / 降级路径须按 `docs/07-observability-driven-dev.md` §2.1 做「记录并重抛 / 记录并回退兜底态」的结构化诊断（黑匣子 §3），禁止裸吞；关键状态切换（如 `Idle → Processing → Success/Failed`）须留痕。
- 不可变默认：输入 / 输出契约优先不可变（值对象 / 只读），减少隐性状态契约。
- 单一职责 + 窄接口：一个函数只兑现一个契约，接口隔离（ISP）。
- 显式边界校验：入口处校验前置条件，早失败（fail-fast）。

> 以上基线为**唯一权威**；模板与 skill 只引用本小节，不重定义。

### 2.6 契约记录规范（四要素 + 域-序号编号，唯一权威）

契约不仅要「写到位」（见 §2.5），还要「写得可追溯」。每条契约须以统一格式记录，使其带出处、可交叉引用、防漂移。

**四要素（每条契约必标）**

| 要素 | 含义 | 示例 |
|------|------|------|
| 归属模块 | 哪个模块 / 文件拥有并兑现该契约 | `Shared/VisionDetector.swift`、`300-design.md §4` |
| 方向 | 调用方 → 被调方 / 生产者 → 消费方 / 输入 → 输出 | `detect(_:) -> [Detection]`、`RENDER-001 输出 -> 下游` |
| 不变性 | 跨调用必须成立的约束（坐标、字段语义、口径、行为） | 原点左上 / `y` 向下 / `0..1`；返回 `[]` 非 `nil` |
| 真值来源（provenance） | 该契约可被校验的具体出处（代码 / ADR / 版本文档章节），供交叉引用与防漂移 | `Shared/...swift`、`adrs/adr-002.md`、`400-build.md §1.2` |
- **诊断日志须反查 provenance**：运行时诊断快照的 `Input Snapshot`（`docs/07-observability-driven-dev.md` §3）应引用本要素出处，使日志可被交叉引用、防漂移（呼应 07 §2.4）。

- **四要素是 §2.5 质量基线的「记录载体」**：质量维度（错误契约 / 幂等 / 兼容 / 不变量 / 失败语义 / 前置后置）应作为「不变性」项的具体落地，二者互补不重复。
- **编号规则（域-序号）**：契约以 `域-序号` 编号（如 `COORD-001` 坐标、`DETECT-001` 检测、`RENDER-001` 渲染、`ERROR-001` 错误），新增须沿用本规则并登记到对应层级 / 章节；便于跨文档交叉引用与回写。

> 以上记录规范为**唯一权威**；模板与 skill 只引用本小节，不重定义。

### 2.7 失败面契约（独立节，强化 §2.5，唯一权威）

§2.5 规定「错误契约须显式写入」，本节规定「失败面如何表达」。二者互补：前者定义要写什么，本节定义怎么表达失败。

**纯函数式失败语义**
- 检测 / 渲染 / 解析等纯函数式契约，失败面**返回空数组 / 原值 / 默认值，绝不返回 `nil` 中断调用方**（与既有先例一致：如 `drawBoxes` / `maskOutsideKeepBubbles` 返回 `image`）。
- 区分两类失败表达：**同步入口**可返回空 / 原值不抛（零改动兼容既有调用方）；**需区分失败原因的后台入口**才抛具体错误（如 `VisionDetectorError`），由调用方按需取用。

**严禁静默危险失败**
- 安全 / 打码类契约即使「成功返回一个外观正常的正常值」，其真正失败（如贴图缺失、无遮蔽目标）**无法从返回值区分**——必须在调用前拦截，并以**显式错误态**暴露（如 `renderError = .stickerMissing`），**禁止依赖返回值兜底**。
- 最危险失败模式：调用方看到外观正常的原图，误以为已打码 / 已处理而直接使用（如直接分享隐私截图）。此类「成功假象」比显式失败更有害，须在契约中明确禁止。
- 安全 / 打码类失败除显式错误态外，还须按 `docs/07-observability-driven-dev.md` §3 输出结构化诊断快照（含 `Input Snapshot` / `Resource Metrics`），便于 AI 一次定位（呼应 07 §2.1 / §2.3）。

> 以上失败面契约为**唯一权威**；模板与 skill 只引用本小节，不重定义。

### 2.8 契约只读纪律与断言门禁（唯一权威）

§2.5/§2.6/§2.7 规定契约「写到位、可追溯、失败面怎么表达」；本节规定「契约文件怎么被机器校验、AI 怎么对待契约」，把 §5 演进治理的「破坏性变更走 dm-adr」升级为**机器化卡口**：AI 在关键节点被强制先校验、再行动。

**机器可校验契约（门禁成立前提）**
- 关键契约（API / Schema / 跨文件调用不变性）须有**可 parse 的单源真理文件**，至少其一：`OpenAPI` / `JSON Schema` / `Protobuf` / Swift `Protocol` / 显式 `Contract` 类型（如 `DetectorContract.swift`）。纯 Markdown 契约（如 `400-build.md` 行为契约表）无法自动校验，须尽可能提炼为上述可 parse 形式，或至少保证字段可被脚本提取。
- `templates/project/docs/03_CONTRACTS_AND_API.md` 的接口/Schema 设计须以 `JSON Schema` 等可校验格式承载，作为门禁输入。

**契约只读纪律（AI 操作约束）**
- 契约文件视为**只读**：AI 改实现代码前，先对契约文件做 `diff`，确认改动不打破契约；**严禁 AI 自行改写契约本身**。
- 确需改契约时分级处理，与 §5 一致：破坏性 / 改语义 → 先走 `dm-adr` 申请，调用方适配后再回写；纯增量追加新条目 → 允许，但须在 PR 描述显式标注「纯增量」，并回写编号（无主防护）。

**自动化断言门禁（Contract Assertion Gate，三道卡口）**
- **Gate 1 改前卡口（Pre-Implementation）**：AI 写第一行业务代码前，先读取并 `diff` 契约文件，确认本次修改不破坏既有契约；若触及契约，先向用户提出申请、获许可才继续。不看契约，不准动代码。
- **Gate 2 改后卡口（Post-Implementation）**：AI 完成多文件修改、准备告知用户「改好了」之前，须先在后台静默运行本地门禁（如 `xcrun swiftc -parse`、`python3 package_dist.py --verify`、`MANIFEST` 哈希校验、JSON Schema 校验）。**门禁没绿（编译不过 / 断言失败 / 哈希对不上）绝对不向用户邀功**——直接拦截输出，把终端报错原样抛回自身，在契约框架内自我修复，直到门禁变绿。
- **Gate 3 交付卡口（Delivery）**：用户指令「提交代码 / 打包 `dist/` / 调 `dm-commit`」时，触发最终门禁，校验 `MANIFEST.json` 文件清单、`sha256` 指纹与 `contract_verified` 状态是否全部对齐；未对齐即报错抛回，禁止带病合并。
- 门禁范式（SHA256 清单 + `contract_verified` 字段 + `--verify` 失败即非 0 退出）见 `samples/contract-gate/`；执行入口与三阶段闭环见 `skills/dm-contract-gate.md`。

> 以上「契约只读 + 断言门禁」为**唯一权威**；模板与 skill 只引用本小节，不重定义。

## 5. 契约演进治理（唯一权威）

契约是长期演进资产。06 定义「怎么写契约」，本节定义「契约变了怎么办」，填补 06 此前缺失的变更管理。

- **破坏性变更须走 dm-adr**：任何破坏既有「不变性」的契约改动（含签名、字段、坐标口径、失败面行为）**必须**提交 ADR（`dm-adr`），不得直接就地改写本文件 / 版本文档后破坏调用方。ADI 记录取舍与迁移路径，调用方可据此适配。
- **纯增量 PR 标注**：新增不破坏既有的契约（新接口 / 新域）可直接追加，但须在 PR 描述显式标注「新增 / 纯增量」，便于审阅者快速识别无破坏性。
- **无主文档防护**：本文档（及项目契约总目录）为通用契约长期载体；任何版本规划（`vX.Y-*` / `mvp-v*`）若引入新接口 / 契约，**必须回写对应章节**并登记编号，避免契约散落各版本文档、变成无人维护的无主文档。
- **编号顺延留痕**：契约编号顺延 / 修正（如版本重排）须注明原编号与原因，保持可追溯，不静默改写历史引用。

> 以上演进治理为**唯一权威**；模板与 skill 只引用本节，不重定义。

# 契约式开发（Contract-Based Dev）

## 1. 概述与导航 <a id="overview"></a>

定义 dev-meta 中「先定契约、后实现」的统一规范。契约是模块 / 函数间、版本内模块间、实现与测试间的**可验证约定**，先于编码确立，以降低集成风险、避免「签名写了但行为没人管」。

本文档是契约式开发的**唯一权威**：模板与 skill 只引用、不重定义；本文档内每条规则**只定义一次**，其余出现处一律写指针。

> 规范地图（块 → 锚点）、规则指针卡、上游来源与落地载体，统一见 **§11**。

### 1.1 契约三层级 <a id="contract-levels"></a>

| 层 | 粒度 | 定义 | 主要载体 |
|----|------|------|----------|
| **L1 接口 / API** | 基线级 | 模块间调用顺序、前置条件、返回值 / 错误码约定 | `templates/project/docs/03_CONTRACTS_AND_API.md` §2；`400-build.md` §1.2 |
| **L2 Feature** | 版本级 | 本版本作为整体对外的输入 / 输出 / 依赖 / 边界 | `300-design.md`（架构与分层 / 数据流与状态机） |
| **L3 关键行为** | 测试级 | 算法 / 隐性契约函数的给定场景预期（given-when-then） | `400-build.md` §3 各 Step 的「关键行为契约」小节 |

> 三层是**粒度维度**（纵向）；「域-序号」是**主题维度**（横向，见 §4.3）。一条契约同时具备两者：**层决定它写在哪个载体，域决定它的编号前缀与所属契约文件**（见 §6.2）。

## 2. 契约层级与流转 <a id="contract-level-flow"></a>

### 2.1 L1 接口 / API 契约（基线级） <a id="level-l1"></a>

- **定义**：模块间调用顺序、前置条件、返回值 / 错误码约定。
- **载体**：`templates/project/docs/03_CONTRACTS_AND_API.md` §2（接口契约模板）；`templates/versions/vX.Y-<slug>/400-build.md` §1.2（版本内模块共用的 API 契约）。
- **时机**：项目初始化阶段，架构基线完成后建立契约基线（见 `docs/01-project-dev-flow.md` §3.3）；每个版本在 400-build 中维护。
- **字段**：接口名 / 方法 / 入参 / 出参 / 错误码 / 调用顺序 / 前置条件 / 返回值约定。

### 2.2 L2 Feature 契约（版本级） <a id="level-l2"></a>

- **定义**：本版本作为整体对外的输入 / 输出 / 依赖 / 边界（版本已收敛为单一业务场景，故契约粒度即版本粒度）。
- **载体**：`docs/02-version-rules.md` §5 300-design「架构与分层 / 数据流与状态机」（落地于 `300-design.md`）。
- **时机**：版本设计阶段（300-design），先于 400-build 实现。
- **字段**：版本号 / 名称 / 输入 / 输出 / 依赖（模块）/ 边界（失败、并发、配额等）。

### 2.3 L3 关键行为契约（测试级） <a id="level-l3"></a>

- **定义**：对算法类 / 有隐性契约（幂等、并发去重、异常分支、降级取舍）的函数，规定「给定场景下的预期行为」（given-when-then）。这是**行为规定**，不是测试实现。
- **载体**：`templates/versions/vX.Y-<slug>/400-build.md` §3 各 Step 明细内的「关键行为契约」小节。
- **适用范围**：仅算法类 / 隐性契约函数必填；薄胶水 / CRUD 函数可省略。
- **字段**：函数 / 场景 / 预期（given-when-then）。
- **落地**：由 `dm-dev-step` 据此生成真实单测。

### 2.4 三层关系与流转 <a id="level-flow"></a>

- L1 定模块边界 → L2 定 Feature（版本）边界 → L3 定函数行为；**下层契约不得违背上层**。
- 三者共同构成「契约式开发」骨架：先契约、后实现、再测试。

## 3. 契约质量基线 <a id="quality-baseline"></a>

契约不仅要「写在哪里」，还要「写到位」。以下维度是**一份合格契约的最低基线**，三层各自按需包含；缺失即视为契约不完整，须在规划 / grill 阶段补齐。

### 3.1 L1（接口 / API）必含维度 <a id="quality-l1"></a>

- **错误契约**：错误码枚举、异常分层、是否可重试，显式写入（禁止散落裸 `throw`）。
- **幂等性**：标注接口是否幂等（尤其写操作 / POST），作为重试与并发去重依据。
- **兼容契约**：变更遵循「加字段不删、不改语义」；破坏性变更须版本化（版本号 / 路径）。
- **超时与限流**：明确 SLA、超时、限流（429）行为。

### 3.2 L2（Feature）必含维度 <a id="quality-l2"></a>

- **失败语义**：边界不只用词（失败 / 并发 / 配额），须写明失败后的状态与可恢复性。
- **前置 / 后置条件**：用 requires / ensures 风格写明函数级契约（Design by Contract）。
- **依赖方向**：模块依赖图单向无环，避免循环契约。

### 3.3 L3（行为）必含维度 <a id="quality-l3"></a>

- **不变量（Invariant）**：标注跨调用的状态不变量（如缓存命中下限、队列非空不可关闭）。
- **契约变更即测试**：行为契约变更须驱动回归测试重跑（落地分层见 §10）。

> 质量维度由 §4.1 的「四要素」承载记录（二者互补不重复）。跨层 Clean Code 编码约定**不属契约维度**，统一见 `docs/09-ai-architecture-guide.md` §6。

## 4. 契约记录规范 <a id="record-spec"></a>

契约不仅要「写到位」（见 §3），还要「写得可追溯」。每条契约须以统一格式记录，使其带出处、可交叉引用、防漂移。

### 4.1 四要素（每条契约必标） <a id="record-four-elements"></a>

| 要素 | 含义 | 示例 |
|------|------|------|
| 归属模块 | 哪个模块 / 文件拥有并兑现该契约 | `Shared/VisionDetector.swift`、`300-design.md §4` |
| 方向 | 调用方 → 被调方 / 生产者 → 消费方 / 输入 → 输出 | `detect(_:) -> [Detection]`、`RENDER-001 输出 -> 下游` |
| 不变性 | 跨调用必须成立的约束（坐标、字段语义、口径、行为） | 原点左上 / `y` 向下 / `0..1`；返回 `[]` 非 `nil` |
| 真值来源（provenance） | 该契约可被校验的具体出处（代码 / ADR / 版本文档章节），供交叉引用与防漂移 | `Shared/...swift`、`adrs/adr-002.md`、`400-build.md §1.2` |

- **状态是第五项必标内容**：每条契约还须标注 `[CURRENT]` / `[PLANNED]` / `[HISTORY]`（定义见 §4.2，一条一标，可机检）。
- **诊断日志须反查 provenance**：运行时诊断快照的 `Input Snapshot`（`docs/07-observability-driven-dev.md` §3）应引用本要素出处，使日志可被交叉引用、防漂移（呼应 07 §2.4）。
- **四要素是 §3 质量基线的「记录载体」**：质量维度（错误契约 / 幂等 / 兼容 / 不变量 / 失败语义 / 前置后置）应作为「不变性」项的具体落地，二者互补不重复。

### 4.2 状态生命周期（`[CURRENT]` / `[PLANNED]` / `[HISTORY]`） <a id="contract-state-lifecycle"></a>

> 本节是三态标记的**唯一权威定义**；`docs/02-version-rules.md` §6.2（S3）与各样例只引用本节。

**三态定义**

| 状态 | 含义 | 可否据以判定实现 |
|------|------|------------------|
| `[CURRENT]` | 现行契约：实现已落地，判据生效 | ✅ 可以（不符即缺陷） |
| `[PLANNED]` | 已立规、实现未落地：接口先冻结，实现待补 | ❌ 不可以（占位，不构成缺陷） |
| `[HISTORY]` | 已被取代 / 过时：索引保留一行，正文迁归档 | ❌ 不可以（仅追溯） |

**记录规则**
- **一条一标**：每条契约（按契约文件的锚点计，见 §7.2）**有且仅有一个**状态标记，写在条目头部，**规范形为 ``  - 状态：`[CURRENT]` ``** —— 结构 lint 只认此形态（§8.4）。
- **粒度是「条」不是「文件」**：不得整文件只标一个状态，也不得同一契约内标两次。
- **状态与正文自洽**：`[PLANNED]` 条目不得写成已完成语气；`[HISTORY]` 条目不得继续充当判据。
- **说明性提及不计**：标题 / 引言 / 索引表 / 规范说明中出现的 `[CURRENT]` 等字样**不算状态标记**（首锚点之前的区域整体不参与按条校验），故手册与索引可自由引用三态词。

**翻牌规则（与 `docs/02-version-rules.md` §6.2 对齐）**

| 时机 | 动作 |
|------|------|
| S1 Contract & ADR（冻结接口） | 新接口可先落 `[PLANNED]` 占位（尚未实现）；已实现的落 `[CURRENT]` |
| S3 Standard Finalization（实测数据回填） | `[PLANNED]` → `[CURRENT]`（阈值 / 口径由实测数据定案） |
| 契约被取代 / 废弃 | 标 `[HISTORY]`，正文按 §6.5 迁入归档目录，索引保留一行 + 归档指针 |

**禁止事项**
- **禁止无状态契约**：缺状态标记的契约视为**契约不完整**，规划 / grill 阶段须补齐。
- **禁止在契约正文写「代码现状」**：现状会腐化且必然误导 —— 理由与实证见 §7.3（不在此复述）。

**机检**：结构 lint 按锚点块校验「一条一标」（§8.4）。

### 4.3 编号规则（域-序号） <a id="record-domain-numbering"></a>

- 契约以 **`域-序号`** 编号，如 `COORD-001` 坐标、`DETECT-001` 检测、`RENDER-001` 渲染、`ERR-001` 错误面。
- 新增契约须沿用本规则并**登记到对应层级 / 契约文件与索引**（§6.4），便于跨文档交叉引用与回写。
- **域从哪来、怎么写、一词一域、可否改名** —— 见 **§6.3（域分类与命名参考）**，本节不复述。
- **编号一经分配不得重编**（重编即全仓引用断裂）；确需顺延 / 修正须注明原编号与原因（§9）。

## 5. 失败面契约 <a id="failure-face"></a>

§3.1 规定「错误契约须显式写入」，本章规定「失败面如何表达」—— 前者定义写什么，本章定义怎么表达失败。

### 5.1 纯函数式失败语义 <a id="failure-pure-functions"></a>

- 检测 / 渲染 / 解析等纯函数式契约，失败面**返回空数组 / 原值 / 默认值，绝不返回 `nil` 中断调用方**（与既有先例一致：如 `drawBoxes` / `maskOutsideKeepBubbles` 返回 `image`）。
- 区分两类失败表达：**同步入口**可返回空 / 原值不抛（零改动兼容既有调用方）；**需区分失败原因的后台入口**才抛具体错误（如 `VisionDetectorError`），由调用方按需取用。

### 5.2 严禁静默危险失败 <a id="failure-no-silent-danger"></a>

- 安全 / 打码类契约即使「成功返回一个外观正常的正常值」，其真正失败（如贴图缺失、无遮蔽目标）**无法从返回值区分** —— 必须在调用前拦截，并以**显式错误态**暴露（如 `renderError = .stickerMissing`），**禁止依赖返回值兜底**。
- 最危险失败模式：调用方看到外观正常的原图，误以为已打码 / 已处理而直接使用（如直接分享隐私截图）。此类「成功假象」比显式失败更有害，须在契约中明确禁止。
- 安全 / 打码类失败除显式错误态外，还须按 `docs/07-observability-driven-dev.md` §3 输出结构化诊断快照（含 `Input Snapshot` / `Resource Metrics`），便于 AI 一次定位（呼应 07 §2.1 / §2.3）。

## 6. 契约资产组织与命名 <a id="asset-organization"></a>

> §4 规定**一条**契约怎么写；本章规定**一批**契约放在哪、怎么找、怎么退场 ——「项目契约总目录」的定义即在此。

### 6.1 载体形态与规模阈值 <a id="asset-size-thresholds"></a>

| 形态 | 适用规模 | 结构 | 升级触发条件 |
|------|----------|------|--------------|
| **单文件** | 契约 ≤ 30 条或 ≤ 300 行 | 项目 `docs/03_CONTRACTS_AND_API.md` 单文件（模板见 `templates/project/docs/03_CONTRACTS_AND_API.md`） | 超过任一阈值 → 拆目录 |
| **目录 + 索引门面** | 30 条以上 / 单文件 >300 行或 >30KB | `契约目录/`（正文按域分文件）+ `索引文件`（只放目录 / 状态 / 链接） | 单域文件 >200 行 → 该域再拆 |
| **分级（大型）** | 多模块 / 多仓库 | L1 契约进契约目录；L2 / L3 随版本文档（`300-design` / `400-build`） | — |

> 阈值是**建议值**，真正的判据有**两条**：① **「查一条契约是否需要全量读整份文档」** —— 需要，就该拆；② **变更节奏不同则分文件** —— 生命周期差异大的资产（如可增删的**高频目录** vs 低频接口契约）混在一份文件里，会互相污染变更节奏与评审成本。**除这两条外，不要为「看起来整齐」而拆。**

**体积预算对照表**（唯一一处集中登记，其余章节只引用本表）

| 对象 | 上限 | 依据 |
|------|------|------|
| 单文件契约（未拆前） | ≤ 300 行 | 本表上行 |
| 索引门面 | ≤ 150 行 | §6.2 |
| 单个域文件 | ≤ 200 行 | §6.2 / §6.8 验收判据 3 |

### 6.2 目录式组织规范 <a id="asset-directory-layout"></a>

- **索引门面**（如 `docs/00_CONTRACTS.md`）：只承载「目录 / 状态 / 链接 + 引用规则」，**不含任何契约正文**；建议 ≤150 行。
- **域文件**（如 `docs/contracts/02-render.md`）：按**域**聚合（域前缀相同的契约同文件，如 `RENDER` / `USER-SELECT` 同属渲染域），单文件 ≤200 行。
- **命名**：`NN-<domain>.md`，全小写连字符；与既有目录（`adrs/` / `designs/`）风格一致。
- **ID → 文件映射唯一**：一个域前缀只落一个文件；新增域须在索引登记并分配文件，不得散落。
- **只搬不重编**：物理搬迁时**契约编号不变**，逐字搬迁、语义零漂移（编号变了，全仓引用即断）。

**域 → 文件 → 锚点前缀 映射表（拆分的施工图：先定表，再动手）**

| 域文件 | 承载域（编号前缀） | 锚点前缀 | 典型内容 |
|--------|-------------------|----------|----------|
| `01-<domain>.md` | `COORD` / `DETECT` | `coord-` / `detect-` | 坐标系与检测层 |
| `02-<domain>.md` | `RENDER` / `USER-SELECT` | `render-` / `user-select-` | 渲染与用户选择 |
| `NN-<domain>.md` | … | … | … |

- **一文件可承载多域**：域少而相邻时**合并**（如上表 `RENDER` + `USER-SELECT`），按「**读者一次要查完的范围**」聚合，**不按前缀数量机械 1:1 拆**。
- **锚点前缀 = 域前缀的 kebab 化**：`RENDER-004` 的 slug 以 `render-` 开头（如 `render-host-dispatch`），看前缀即可判断归属文件。
- **文件序号即阅读顺序**：`NN` 从 `01` 起按「底层数据结构 → 用例编排 → 外部出口」排列；**序号一经分配不复用**（删文件后留空号，不重排）。
- **映射表与索引同址登记**（放索引门面内），使「一条契约该落哪」无需翻找。

### 6.3 域分类与命名参考 <a id="asset-domain-naming"></a>

> 用途：**立项时一次性定下域表**（登记在索引门面内），避免 `ERR` / `ERROR`、`MEM` / `MEMORY` 并存这类漂移。**A / B / C 为硬性规则**；「通用域族参考」与「反例清单」属可裁剪参考，见 `templates/project/docs/03_CONTRACTS_AND_API.md` 附录。

**A. 域选取判定法（按优先级，取第一个命中）**

| 序 | 判据 | 说明 |
|----|------|------|
| 1 | **归属模块**（默认） | 谁兑现该契约；**「改它时最先要跟着改的是谁」** —— 那就是它的域 |
| 2 | **跨模块关注点** | 错误面 / 观测 / 并发 / 内存等横切关注点 → **独立成域**（`ERR` / `OBS` / `CONC` / `MEM`），**不寄生业务域** |
| 3 | **数据流阶段** | 仅当阶段边界 ＝ 模块边界时使用（`LOAD` / `PIPE` / `EXPORT`） |

- **一条契约只落一个域**：不允许一条挂两域；跨域内容应拆成两条（各归其域）或归到主导域。
- **域表中未登记的域不得临时使用** —— 临时新增即「登记不完整」，须先补域表再写条目。

**B. 域前缀命名硬规则**
1. **全大写 ASCII**，**无连字符、无数字** —— 数字属序号部分（写 `RENDER-004`，不写 `RENDER-2-001`）。
2. 长度 **2–8 字符**，**单音节缩写优先**（`MEM` 优于 `MEMORY`，`ERR` 优于 `ERROR`）。
3. **一词一域**：同一含义只立一个域，不得 `ERROR` / `ERR` 并存，也不得 `MEM` / `MEMORY` 并存。
4. **域一经登记不得改名**（改名 ＝ 全仓引用断裂）；需要拆分时**新立域**，旧域走 ADR + 标 `[HISTORY]` 归档（§6.5）。
5. **不得占用保留命名空间**（见 C）。

**C. 命名空间互斥表**

| 命名空间 | 形态 | 含义 | 权威 |
|----------|------|------|------|
| `S0`–`S7` | 固定 8 个 | 版本**施工步**（工序） | `docs/02` §6.2 |
| `GUARD-xx` | 域-序号 | 版本级**防腐红线** | `docs/02` §3.5 |
| `L1` / `L2` / `L3` | 固定 3 个 | 契约**层级**（粒度） | 本文 §1.1 |
| `O1` / `O2` / `O3` | 固定 3 个 | **观测**层级（断言 / 埋点 / 回读） | `docs/07` §2.6 |
| `<DOMAIN>-NNN` | 域-序号 | 契约 **ID** | 本文 §4.3 / §6.2 |
| `NN-<domain>.md` | 文件序号-域 | 契约**文件**（阅读顺序，序号不复用） | 本文 §6.2 |
| `LINT-xx` | 域-序号 | 结构 lint 校验项（文档层机检） | 本文 §8.4 |
| `Gate N` | 固定 3 个 | 门禁卡口（改前 / 改后 / 交付） | 本文 §8.3 |
| `TF` / `Transaction Flow` | — | **历史术语**，新文档不使用 | 门禁结构检查 |

> 各命名空间含义唯一、**不得交叉**：不得把契约 ID 写成 `GUARD-11`，也不得把防腐红线写成 `L4-001`。

### 6.4 索引表范式 <a id="asset-index-table"></a>

索引表是全仓**唯一查找入口**，每行至少含四列：

| 编号 | 一句话 | 状态 | 正文 |
|------|--------|------|------|
| `RENDER-004` | 覆盖集按宿主分派 | `[CURRENT]` | `docs/contracts/02-render.md#render-host-dispatch` |

- **新增 / 废弃契约必须同步本表**，否则契约即成为「无主」。
- 状态列与正文状态标记必须一致（§4.2）；链接可达与状态一一对应由结构 lint 校验（§8.4）。
- 索引**不写「谁引用了我」** —— 反向索引由消费方自证（§7.1）。

### 6.5 归档规则（不删除） <a id="asset-archive-rule"></a>

| 项 | 规则 |
|----|------|
| 归档判据 | 段落只描述「当时状态 / 已完成 / 盘点 / 验证记录」，且**对当前决策无约束力** |
| **不归档** | 解释「**为什么**」的决策理由（取舍、教训、反例）—— 属防回归资产，误伤代价高，**一律留在正文** |
| 做法 | `git mv` 迁入归档目录（保留历史）→ 标 `[HISTORY]` → 索引保留一行并注明归档位置 |
| 纪律 | **不直接删除**（保留可追溯性）；归档内容不再作为判据，但须保留指向现行契约的指针 |

### 6.6 外部 / 跨项目契约 <a id="asset-external-ssot"></a>

- 外部 SSOT（模型包、SDK、上游服务等）**只留指针 + 契约版本号**，**不复制正文** —— 复制即产生第二真值源。
- 指针须含**可判定的版本标识**（版本号 / commit）；该版本一旦变化，视为契约变更，须走 §9 治理。
- 交付物形式的契约以其自身 `README` + 指纹清单（`MANIFEST`）为入口，接收方按其迁移清单接入。

### 6.7 落地路径（Adoption） <a id="asset-adoption"></a>

**新项目最小落地**（四步渐进，不必一次到位）：

1. 单文件契约（`docs/03_CONTRACTS_AND_API.md`）：每条含**四要素 + 状态**（§4.1 / §4.2）。
2. 立索引：文件顶部加一张「编号 | 一句话 | 状态 | 正文」表（§6.4）。
3. 接结构 lint：跑 `samples/contract-lint/`，纳入交付前门禁（§8.4）。
4. 超阈值再拆目录（§6.1）：`git mv` + 脚本批量改引用，编号不变（§6.2）。

**存量项目渐进迁移**（顺序不可颠倒，每步可独立提交 / 回滚）：

1. **立索引**（不改正文）→ 先让契约有唯一查找入口。
2. **补状态标记**（一条一标）→ 让「现行 / 规划 / 过时」可机检。
3. **补语义锚点**（§7.2）→ 让引用可精确定位，摆脱对 §号 的依赖。
4. **接结构 lint** → 让上述约定**不退化成口头约定**。
5. **物理拆分**（可选，超阈值才做）→ 按 §6.8 执行。

> 迁移红线：**编号不变、语义逐字搬迁**；引用改造**必须脚本批量 + `grep` 复核**，禁止手改。

### 6.8 拆分执行与验收 <a id="asset-split-checklist"></a>

**前置**（两条都须满足，否则先回 §6.7 补课）：

1. §6.1 阈值已触发（或「查一条需全量读」已成立）；
2. §6.7 存量迁移第 1–4 步已完成 —— 索引、状态标记、语义锚点、结构 lint 均已就位。

**步骤（4 步，禁止跳步；每步一个原子 commit，可单独 `git revert`）**

| # | 步骤 | 要点 |
|---|------|------|
| 1 | **冻结编号集合** | 拆分前导出全部契约编号落盘，作为「零丢失」基准（命令见下） |
| 2 | **先定映射表，再切分** | 按 §6.2 写「域 → 文件 → 锚点前缀」映射表；按映射表 `git mv` 建目录与域文件，**按域边界切**（不按节号切）；**映射表未覆盖的段落 → 报错中止**，不产出半成品 |
| 3 | **补齐条目要素** | 每条契约补语义锚点（§7.2）与状态标记（§4.2）；索引门面按 §6.4 重写为「目录 / 状态 / 链接」 |
| 4 | **批量改引用 + 复跑 lint** | 带路径引用**脚本批量**替换（禁止手改）、`grep` 分类复核；跑结构 lint 至全绿 |

```bash
# 步骤 1：冻结编号集合（拆分前）
grep -oE '\b[A-Z][A-Z0-9]*-[0-9]+' <契约文件> | sort -u > /tmp/before.txt

# 步骤 4：拆分后复跑结构 lint（§8.4）
python3 contract_lint.py --contracts-dir docs/contracts
```

**验收判据（5 项，全过才算拆完）**

| # | 判据 | 验证方式 |
|---|------|----------|
| 1 | **编号零丢失、零新增** | 拆分后编号集合与 `before.txt` `diff` 一致 |
| 2 | **正文逐字搬迁** | 除新增的「锚点（heading 内联）+ 状态行」外 diff 为空（人工复核 + 段落比对） |
| 3 | **体积达标** | 索引门面 ≤150 行；每个域文件 ≤200 行（见 §6.1 预算表） |
| 4 | **结构 lint 全绿** | `contract_lint.py`（§8.4 四查） |
| 5 | **引用形态统一** | 全仓 `grep` 无旧形态（带旧路径）引用残留；仅余纯语义引用（如「见 `RENDER-004`」） |

**不拆的红线（反面清单）**
- **不得为「看起来整齐」而拆** —— 唯一动机是检索成本（§6.1）；未触发阈值就不拆。
- **不得夹带语义修订**：拆分批次**只搬不改**；要改语义另开批次（破坏性变更走 §9）。
- **不得搬下游**：版本文档四件套（`200` / `300` / `400` / `500`）留在原位；决策理由（「为什么」）不进归档（§6.5）。
- **不得重编号或重排章节号**：编号一变，全仓引用即断。

## 7. 引用与定位纪律 <a id="reference-discipline"></a>

### 7.1 引用方向：单向 <a id="ref-one-way"></a>

| 方向 | 对象 | 规则 |
|------|------|------|
| ✅ 允许·向上溯源 | 源码真值、ADR、外部 SSOT | 仅用于**溯源**；判据仍以契约写明的「不变性」为准 |
| ❌ 禁止·反向依赖下游 | 版本文档、冲刺 / 计划、上层规格与设计文档 | 这些文档**引用契约**；契约若反向引用，改一次计划就要动契约 |
| ❌ 禁止·反向索引 | 「谁引用了我」清单 | 消费方须在**自己文档内**声明「引用 `<契约文件>#<锚点>`」 |

**不变性自足原则**：每条契约的「不变性」须在正文内写完整 —— 读者**不需要打开任何其他文档**即可据以判定实现是否正确。

### 7.2 定位形态：语义锚点 <a id="ref-semantic-anchor"></a>

- **引用形态**：`<契约文件>#<语义 slug>`，如 `docs/contracts/02-render.md#render-host-dispatch`。
- **锚点用语义 slug，不用数字编号**：`#render-host-dispatch` 可读、可一键跳转、可机检；`#render-004` / `§4` 会随编号与章节调整漂移。
- **落地方式**：契约条目 heading **行末内联**显式 HTML 锚点（`### RENDER-004 覆盖集按宿主分派 <a id="render-host-dispatch"></a>`）；独立成行亦可，结构 lint 两种形态都认。用显式锚点而非依赖中文 heading 自动锚点 —— 后者不可读、不可控。
- **slug 格式**：`^[a-z][a-z0-9]*(-[a-z0-9]+)+$`，全小写连字符，**全仓唯一**。
- **ID 与 slug 并存**：ID（如 `RENDER-004`）是稳定标识，slug 是可读定位符；引用一律用 slug。
- **规范文档同样适用**：本文档各规范块亦带锚点（见 §11.1），跨文档引用本规范时应优先用锚点。

### 7.3 禁写现状 + 可执行验证 <a id="ref-no-status-prose"></a>

- 契约正文**禁止**写「代码现状」「当前实现是……」—— 现状会腐化，腐化后必然误导判定。要写就写成**可执行断言**：测试名 / `grep` 命令 / 编译约束 / 脚本。
- **实证（为什么必须禁）**：某项目契约正文写「主 App 使用 `mainApp` 覆盖集」，而代码实际走 `default` —— 文档与实现相反，读者却无从察觉。**状态与现状都不可机检时，文档必然误导**。这正是 §4.2 状态标记与本节「禁写现状」的动因。
- 可执行验证的三种合法形态：① 指向单测（如 `XxxTests.testYyy`）；② 指向 `grep` 式静态扫描（含期望命中数）；③ 指向编译器 / 类型系统强制。

## 8. 门禁与自动校验 <a id="gate-and-lint"></a>

本章规定「契约文件怎么被机器校验、AI 怎么对待契约」：把 §9 的「破坏性变更走 dm-adr」升级为**机器化卡口** —— AI 在关键节点被强制先校验、再行动。

### 8.1 机器可校验契约（门禁成立前提） <a id="gate-machine-checkable"></a>

- 关键契约（API / Schema / 跨文件调用不变性）须有**可 parse 的单源真理文件**，至少其一：`OpenAPI` / `JSON Schema` / `Protobuf` / Swift `Protocol` / 显式 `Contract` 类型（如 `DetectorContract.swift`）。纯 Markdown 契约（如 `400-build.md` 行为契约表）无法自动校验语义，须尽可能提炼为上述可 parse 形式；其**文档形态**则由 §8.4 的结构 lint 校验。
- `templates/project/docs/03_CONTRACTS_AND_API.md` 的接口 / Schema 设计须以 `JSON Schema` 等可校验格式承载，作为门禁输入。

### 8.2 契约只读纪律（AI 操作约束） <a id="gate-read-only"></a>

- 契约文件视为**只读**：AI 改实现代码前，先对契约文件做 `diff`，确认改动不打破契约；**严禁 AI 自行改写契约本身**。
- 确需改契约时的分级处理（破坏性 → ADR / 纯增量 → PR 标注）**统一见 §9**，本节不复述。

### 8.3 三道卡口 <a id="gate-three-checkpoints"></a>

- **Gate 1 改前卡口（Pre-Implementation）**：AI 写第一行业务代码前，先读取并 `diff` 契约文件，确认本次修改不破坏既有契约；若触及契约，先向用户提出申请、获许可才继续。不看契约，不准动代码。
- **Gate 2 改后卡口（Post-Implementation）**：AI 完成多文件修改、准备告知用户「改好了」之前，须先在后台静默运行本地门禁（如 `xcrun swiftc -parse`、`python3 package_dist.py --verify`、`MANIFEST` 哈希校验、JSON Schema 校验）。**门禁没绿（编译不过 / 断言失败 / 哈希对不上）绝对不向用户邀功** —— 直接拦截输出，把终端报错原样抛回自身，在契约框架内自我修复，直到门禁变绿。**文档式契约（§6）另须跑结构 lint**（§8.4）。
- **Gate 3 交付卡口（Delivery）**：用户指令「提交代码 / 打包 `dist/` / 调 `dm-commit`」时，触发最终门禁，校验 `MANIFEST.json` 文件清单、`sha256` 指纹与 `contract_verified` 状态是否全部对齐；未对齐即报错抛回，禁止带病合并。
- 门禁范式：产物断言门禁见 `samples/contract-gate/`（SHA256 清单 + `contract_verified` + `--verify` 非 0 退出）；结构 lint 见 `samples/contract-lint/`；执行入口与三阶段闭环见 `skills/dm-contract-gate.md`。

### 8.4 结构 lint（文档层机检） <a id="lint-four-checks"></a>

**四查**（全部针对契约文档本身）：

| 编号 | 校验项 | 违例即失败 |
|------|--------|------------|
| LINT-01 | 引用**零死链** | `<契约文件>#<slug>` 的文件或锚点不存在，或锚点实际不在该文件 |
| LINT-02 | **一条一标** | 某锚点块内**规范状态标记**（``  - 状态：`[X]` ``）数 ≠ 1；说明性文字与首锚点之前的区域**不计** |
| LINT-03 | 锚点**唯一且格式合法** | slug 重复，或不符合 §7.2 格式 |
| LINT-04 | 契约**不引下游** | 契约文件内出现版本文档 / 计划 / 上层规格的路径引用 |

- **参考实现**：`samples/contract-lint/contract_lint.py`（零依赖；退出码 `0` = 全绿 / `1` = 逐条列出违规 / `2` = 用法或 IO 错误）。
- **接入**：**关版本前必跑**（对齐 `docs/02-version-rules.md` §6.2 S7）；`dm-contract-gate` 的 Gate 2 一并执行（§8.3）。

### 8.5 双门禁分工（不可互替） <a id="gate-lint-vs-assert"></a>

| 门禁 | 校验对象 | 手段 | 参考实现 |
|------|----------|------|----------|
| **结构 lint** | 契约**文档本身**（形态：链接 / 状态 / 锚点 / 引用方向） | 纯文本静态检查，零依赖 | `samples/contract-lint/` |
| **断言门禁** | 契约对应的**产物**（语义：编译 / Schema / sha256 / `contract_verified`） | 编译、Schema 校验、哈希指纹 | `samples/contract-gate/` |

> 二者互补且**不可互替**：结构 lint 过了不等于契约语义正确；产物门禁过了不等于契约文档无死链。

## 9. 演进治理 <a id="evolution-governance"></a>

契约是长期演进资产。本章定义「契约变了怎么办」。

- **破坏性变更须走 dm-adr**：任何破坏既有「不变性」的契约改动（含签名、字段、坐标口径、失败面行为）**必须**提交 ADR（`dm-adr`），不得直接就地改写契约 / 版本文档后破坏调用方。ADR 记录取舍与迁移路径，调用方可据此适配。
- **纯增量 PR 标注**：新增不破坏既有的契约（新接口 / 新域）可直接追加，但须在 PR 描述显式标注「新增 / 纯增量」，便于审阅者快速识别无破坏性。
- **无主文档防护**：任何版本规划（`vX.Y-*` / `mvp-v*`）若引入新接口 / 契约，**必须回写对应契约文件与索引**并登记编号（结构见 §6）—— 避免契约散落各版本文档、变成无人维护的无主文档。
- **编号顺延留痕**：契约编号顺延 / 修正（如版本重排）须注明原编号与原因（§4.3），保持可追溯，不静默改写历史引用。

## 10. 测试职责分层 <a id="test-layering"></a>

测试相关内容按以下分层归属，**三处不重复、不冲突**：

| 层 | 产出物 | 谁负责 | 落在哪 |
|----|--------|--------|--------|
| 测什么（场景） | 测试策略、关键场景 | 设计阶段 | `300-design.md` §7 测试策略 |
| 期望什么（行为契约） | 关键行为契约表 | 构建阶段 | `400-build.md` §3 各 Step 明细内的「关键行为契约」小节 |
| 落地实现 | 真实单测代码 | 开发阶段 | `dm-dev-step` 据此生成 |

> 三层分工的唯一权威即本章。`docs/02-version-rules.md` §3.6 仅作指针。

### 10.1 测试基线棘轮

- 每个版本的测试基线（用例数 / 关键断言数）**只升不降**，数值记录于 `300-design.md` §7 测试策略。
- 删除或跳过既有测试，须**显式说明理由**并在 `400-build` §2 对应 Step 标注，**不得静默删除以换取全绿**。
- `dm-close-ver` 收口审计须核对「**测试基线未下降**」；下降且无说明即阻塞收口。

### 10.2 必须走集成 / E2E 的判据

满足**任一**条件即**不得**只靠单元测试交付：

| # | 判据 | 说明 |
|---|------|------|
| 1 | **跨模块 / 跨层** | 产物由 ≥2 个模块、或 2 层以上协作产生 |
| 2 | **产物离开本进程** | 文件 / 网络 / 数据库 / IPC / 系统 API |
| 3 | **平台专属失效模式** | 该失效只在真实平台复现，模拟器或单测环境不复现（`docs/07` §2.6 判据 B） |
| 4 | **轨迹类资产变更** | 须在完整逻辑链路上验证「一次命中」，不得以单测代替（`docs/07` §3.2） |

> 与 `docs/07` §2.6 的 O1/O2/O3 判据同构：**测试层级由「失效模式在哪出现」决定，而非由「哪个好写」决定**。

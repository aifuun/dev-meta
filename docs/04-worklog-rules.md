# Worklog Rules

工作日志规范，定义 `worklog.md` 的结构与记录规则。

## 1. 文件位置

每个项目的 worklog 固定位于：

```
docs/reports/worklog.md
```

## 2. 文件结构

worklog.md 包含以下章节（按出现顺序）：

| 章节 | 是否必填 | 说明 |
|------|----------|------|
| 项目名 + 最后更新时间 | 必填 | 标题与一行 meta |
| 文档说明 | 必填 | 章节用途表 + 记录规则 |
| 每日工作总结 | 必填 | 倒序表格，每行一个日期 |
| 按日期展开的详细日志 | 必填 | 每天的 commit 表 + 其他工作 |
| 近期待办事项 | 必填 | 下一阶段开发任务 |
| 常用脚本与部署方法 | 可选 | 项目有部署需求的加上 |
| 里程碑 | 必填 | 项目关键节点时间线 |

## 3. 记录规则

### 3.1 更新节奏

- **每天结束时更新**，不攒到周末。
- 新增日期时，在「每日工作总结」表格顶部插入一行，并在下方新增对应的日期章节。

### 3.2 每日工作总结

使用 Markdown 表格：

```markdown
| 日期 | 工作总结 |
|------|---------|
| **YYYY-MM-DD** | 一句话概括核心产出，用分号分隔多个事项 |
```

- 倒序排列（最新在上）。
- 粗体日期。
- 总结为自然语言，不罗列 commit hash。

### 3.3 详细日志格式

每个日期一节，包含 commit 表：

```markdown
## YYYY-MM-DD

| Commit | 内容 |
|--------|------|
| `abc1234` | **type**: description |
| `—`      | 非 commit 工作描述 |
```

- commit hash 用短格式（7 位），反引号包裹。
- 内容以 `**type(scope)**: description` 或 `**type**: description` 开头（type 如 feat/fix/refactor/docs/chore）。
- 非 commit 工作（讨论、审查、决策、部署操作）以 `—` 占位 hash，放在「### 其他工作」小节下。

### 3.4 近期待办

```markdown
| # | 待办项 | 方向/说明 | 状态 |
|---|--------|-----------|------|
| 1 | 待办描述 | 简要说明 | ⬜ 待开始 |
```

- 状态使用 `✅ 已完成` / `🔄 进行中` / `⬜ 待开始`。

### 3.5 常用脚本与部署方法（可选）

- 如果项目包含构建/部署脚本，在此记录 `npm scripts` 清单、构建命令、部署流程。
- 部署方式或常用命令变更时同步更新此节。

### 3.6 里程碑

```markdown
| 日期 | 里程碑 |
|------|--------|
| YYYY-MM-DD | 描述 |
```

- 只记录关键交付节点与决策节点。
- 倒序排列。

## 4. 反模式

- ❌ 攒到周末统一补写
- ❌ 在每日总结直接贴 commit hash
- ❌ 待办项常年不更新状态
- ❌ 详细日志与每日总结内容完全重复
